# Web research toolkit

> **Last Updated:** 2026-11-01

The web research toolkit lets an agent search the public web and read public pages, under a guard that decides what the server may request. The vendor research agent is its first user (see [Vendors](../domains/vendors.md#vendor-research-agent)), and the toolkit is written so that other agents can browse with it later. The design is in `docs/superpowers/specs/2026-10-11-vendor-research-web-agent-design.md`.

The agent runs on the organization's own LLM key: whichever key the organization has, the model decides what to search for and which pages to read, and code runs those two actions. There is no search account, no search key and no setup beyond the LLM key; the search engine of a run is picked from that key (see [Search engines](#search-engines-q21-decided-2026-10-31)). By default the newest key does both the research and the analysis; an Admin can choose one key for the research loop and another for the analysis (see [Which key a run uses](../domains/vendors.md#which-key-a-run-uses)).

## Search engines (Q21, decided 2026-10-31)

Every run searches, and the engine is picked from the research key of the run (`searchEngineOf` in `vendorResearch/searchEngineOf.ts`, which reads the provider name and the address of the key row and never the key). The feature still needs nothing beyond the organization's LLM key: no search account, no search key and no environment variable.

| Research key | Engine | What it searches | Cost |
|--------------|--------|------------------|------|
| Anthropic, with the address of the Anthropic API or none (`api.anthropic.com`) | The web search of Claude: the `web_search_20250305` server tool of the key's own provider (`providerSearch.ts`) | The web and the news, with no stated limit of reach | About $10 per 1,000 searches, billed by Anthropic to the key, plus the tokens of the calls. A run makes about 20 to 30 searches (the research settings say so), so about $0.20 to $0.30 in fees |
| Every other key: OpenAI, OpenRouter, Custom (DeepSeek, a local model), Bedrock, and an Anthropic key behind a gateway or a proxy address | The news of the GDELT Project, DOC 2.0 API (`gdeltSearch.ts`) | The news of the last 3 months only | None |
| An Anthropic key whose provider refuses to search (the API answers 400 or 404, for example because web search is turned off for the organization) | Claude's search until the refusal, then GDELT for that search and every later one of the run (`withFallback`) | | |

- **Why the Bing feed went.** The first engine read the public RSS results feed of Bing. It was removed on 2026-10-31, from the product and from development and evaluation. The copyright notice that every Bing feed carries allows rendering its results in an RSS aggregator for personal, non-commercial use only, and asks for Microsoft's written permission for any other use; the Microsoft Services Agreement (14.f.i) limits Bing material to personal, non-commercial use and (3.a.vi) bars impermissible scraping; the `robots.txt` of Bing disallows `/search`, which is the web feed, and the product's own rule is that research reads nothing a site asks robots to leave; and the licensed route is gone, since the Bing Search APIs retired on 2025-08-11 and their successor, Grounding with Bing, needs an Azure account, returns model answers instead of results and forbids storing its output. A commercial product run on customers' servers is outside the notice, so there was nothing to ask for. **The release gate that this page used to carry is closed by this decision.**
- **GDELT.** Its terms allow commercial use without a fee if the GDELT Project is cited, which the run summary does ("News searched with the GDELT Project (last 3 months)", with a link to the project). It needs no account or key, its `robots.txt` is a 404 (so it disallows nothing), and it matches the keywords it is given against its own machine translation of the news in 65 languages. It reaches back 3 months, gives titles and no snippets, and allows one request every 5 seconds from an address. So the engine makes one request for the run and answers every news search of the run from it (see [The search engine](#the-search-engine)). It cannot search the web: a search of kind `web` is refused (see below).
- **Claude's search.** The tool is the basic version, called directly by Claude and eligible for zero data retention (from `web_search_20260209` on, the tool runs inside code execution, which is not). Each search is one small model call that relays the query, four at the same time at most; the sources are returned as clickable links, which the findings keep (both providers require visible, clickable citations, and `FindingRow` renders each source as a link). The key's own provider is the processor of these queries, as it is of the rest of the run. The SDK retries nothing, so a 429 is an ordinary failed search. A search call is a model call of the run and appears in the [trace](#the-run-trace) as `purpose: "search"` with its tokens.
- **OpenAI and the others.** OpenAI's own web search is not built: an OpenAI key searches the news through GDELT. OpenRouter's web plugin, Gemini grounding (its terms bar caching results and using their links to crawl), Azure Grounding with Bing, Brave, Perplexity and public SearXNG instances were looked at and not taken (a key of their own, an account, terms that bar storing, or nothing in them that a product can rely on); the `robots.txt` of Wikipedia's API, Google News and DuckDuckGo disallow their search paths.
- **The run records its engine.** `vendor_research_runs.search_engine` (`anthropic`, `openai` or `gdelt`; `openai` is allowed by the constraint and no run stores it) is the engine the run's searches went to, after a fallback the one it ended on. It is recorded only when at least one search was answered, so a run whose searches the web never answered shows no engine and no credit for news that was never received. The run summary says "Searched with Claude web search" or credits GDELT (see [Vendors](../domains/vendors.md#which-key-a-run-uses)).
- **Turning search off.** An Admin who turns off web search for the organization at the provider makes the provider answer 400: the run falls back to GDELT and still has news.
- **Pages are different.** The page reader obeys each site's `robots.txt`. GDELT's `robots.txt` is asked as well, with the request's own time limit (below).

## The page guard

`read` lets a model choose which URL the server requests, and the model reads text that attackers can write. That is a server-side request forgery surface, so the guard is its own module and not `utils/safeOutboundUrl.ts`: that helper lets private ranges through on purpose (on-premises MLflow and Jira servers) and must not be reused for untrusted URLs. No dependency is added; Node's `net.BlockList` and `https.request` are enough. The search feed is requested through the same guarded fetch.

The agent has no tools of its own. The model can only name a search or a URL, and code decides whether and how it happens. Requests are GET only, to public addresses only, for URLs with a provenance; no secret and no organization data is in the model's context; every budget is hard; the analysis has no actions and its output is bound to a schema and checked against the text; and nothing reaches the risk register until a person accepts it.

### URL policy

Checked first, on every URL, whether the model named it or a redirect did (`publicUrl.ts`).

- `http` or `https` only. No user name or password in the URL. Port empty, 80 or 443. At most 2,048 characters, as written and once the parser has percent-encoded the characters a URL cannot carry.
- The host is a DNS name with at least two labels, each made of letters, digits and inner hyphens (63 characters at most). A trailing dot is removed.
- An IP address in any notation is refused. The URL parser turns `2130706433` and `0x7f.1` into dotted decimal, and `net.isIP` then sees them.
- `localhost`, `*.localhost`, `*.local`, `*.internal` and `*.home.arpa` are refused.
- The fragment is dropped.

### Address policy, checked on the connection

The request is made with `https.request` or `http.request` and a validating `lookup` hook, so the address that was checked is the address that is connected to. There is no gap in which DNS can answer differently (DNS rebinding). Every address the host resolves to must be public, and one non-public address refuses the whole host. An empty answer is refused too.

Not public means any of these ranges. There is one list per IP family, and an address is only checked against its own family's list.

| Family | Ranges |
|--------|--------|
| IPv4 | `0.0.0.0/8`, `10.0.0.0/8`, `100.64.0.0/10`, `127.0.0.0/8`, `169.254.0.0/16`, `172.16.0.0/12`, `192.0.0.0/24`, `192.0.2.0/24`, `192.168.0.0/16`, `198.18.0.0/15`, `198.51.100.0/24`, `203.0.113.0/24`, `224.0.0.0/4`, `240.0.0.0/4` |
| IPv6 | `::/128`, `::1/128`, `::/96`, `::ffff:0:0/96` (blocked as a whole), `64:ff9b::/96`, `64:ff9b:1::/48`, `100::/64`, `2001:db8::/32`, `2002::/16`, `fc00::/7`, `fe80::/10`, `fec0::/10`, `ff00::/8` |

`::/96` (the deprecated IPv4-compatible form), `64:ff9b:1::/48` (local-use NAT64, RFC 8215) and `2002::/16` (6to4) carry an IPv4 address inside them, so an AAAA record under one of them could reach an internal IPv4 address through a translator or a tunnel. `fec0::/10` is the site-local range that RFC 3879 deprecated, still routed inside some networks. An address with a zone id (`fe80::1%eth0`) is not public either.

### Redirects

Followed by hand, at most 4. Every hop goes through the URL policy, the address policy and `robots.txt` again, so a redirect cannot lead to a place the first URL could not. A redirect from https to http is refused. More than 4 redirects make the page unreachable.

### Response limits

| Limit | Value |
|-------|-------|
| Status | 200 only; `guardedConditionalFetch` also takes a 304 on the last hop (see [Records of public databases](#records-of-public-databases)) |
| Content types | `text/html`, `application/xhtml+xml`, `text/plain`, `text/xml`, `application/xml`, `application/rss+xml`; the page reader adds `application/pdf` and `application/x-pdf`, and for an address whose path ends in `.pdf` also `application/octet-stream` and `binary/octet-stream` (see [Reading a PDF](#reading-a-pdf)) |
| Body, after decompression (`gzip`, `br`, and `deflate` in its zlib form when a server sends it unasked) | 2,097,152 bytes, or the limit that the caller sets for the media type of the answer (`maxBytesByType`: the page reader asks for 10,485,760 bytes for a PDF); a longer body is cut there and the stream is closed, so a compressed bomb is not read to its end |
| Time to the response headers of one hop | 12,000 ms |
| The whole fetch, redirects and body included | 20,000 ms |
| Redirects | 4 |

A request carries the bot's User-Agent, `Accept`, `Accept-Encoding: gzip, br` and `Accept-Language: en`, and nothing else: no cookies, no credentials, no `Referer`. Each request has a fresh socket, and TLS certificates are verified. The character set comes from the `Content-Type` header, then from a `<meta charset>` in the first 2 KB of the body, then it is UTF-8.

Why a fetch fails, as the model is told:

| Reason | When |
|--------|------|
| `not_allowed` | The URL or the address policy refused it |
| `blocked_by_robots` | `robots.txt` disallows the page |
| `blocked_by_site` | The site answered 401, 403 or 429 |
| `not_found` | 404 or 410 |
| `unsupported_type` | A content type that is not in the list above (a Word file, an image), or a PDF that cannot be read: a scan with no text, a damaged or encrypted file, one that took too long or needed too much memory |
| `needs_javascript` | An HTML page of at least 20,000 characters with fewer than 500 characters of text, whose own data (Next.js props, JSON-LD, `<noscript>`) holds fewer than 500 characters of text as well, and that the headless browser, when it is on, does not fill either: the text is built by a script |
| `unreachable` | Any other status, a network error, a time limit, too many redirects, an encoding that cannot be decoded |

The page reader does not look for challenge pages. A site that shows one with a 200 answer is read as a page with little text.

### Bot identity and `robots.txt`

The bot says who it is and does not imitate a browser: User-Agent `VerifyWiseResearchBot/1.0 (+https://verifywise.ai)`, product token `VerifyWiseResearchBot`.

Before a page is fetched, and before every redirect hop, the reader asks the `robots.txt` of the origin.

- **Which group.** A group applies when one of its `User-agent` values names exactly `VerifyWiseResearchBot`. The comparison ignores case and a `/version` suffix, so `VerifyWiseResearchBot/1.0` matches and `bot` or `wise` do not. A file may name the bot in several groups, and their rules are combined. Without a group of ours, the `*` groups apply.
- **Which rule.** `Allow` and `Disallow` by the longest match, `Allow` wins a tie, `*` and a trailing `$` work, and a path that no rule matches is allowed. A pattern is never compiled into a regular expression, because the file is written by the site's owner and a pattern with many wildcards would make a backtracking engine run for as long as the site likes.
- **The file.** Fetched through the same guard, with 5,000 ms and 65,536 bytes, under any content type (static hosting often serves it as `application/octet-stream`). The answer is cached per origin for one run, and for 24 hours for all runs when the reader has the shared cache (see [The shared cache](#the-shared-cache)).
- **When the file cannot be had.** A missing file (404, 410) and a site that refuses to show it (401, 403, 429) mean the site has no rules, and everything is allowed. When the URL or the address policy refuses the request for the file (most often because the host resolves to an address that is not public), every page of that origin is refused as `not_allowed` for the run, as the page itself would be. Any other outcome disallows everything on that origin for the run: a 5xx answer, another 4xx status, a time-out, a network error or too many redirects.

### Provenance

A URL may be read only if, in this run, a search returned it, or it is on the vendor's domain or a subdomain of it (whole labels are compared, so `acme.com.evil.example` and `notacme.com` are not on `acme.com`). Anything else is refused, and the model is told to search first. So a page cannot send the agent to an arbitrary address with data in its query string. The one exception to this reading is a host that the [check of the website](#the-research-loop) found closed before the run: its pages are refused as `site_closed` even when a search returned them.

The comparison is made on the **canonical form** of the address (`urlCanon.ts`), so a read may name any spelling of an address that a search returned. `resolveAddress` is the URL policy plus three cleanings that cannot change which page is meant: the parameters that only say who sent the reader (`utm_*`, click ids such as `fbclid`, `gclid` and `msclkid`, mail campaign ids) and the markers of an amp page in the query (`amp=1`, `outputType=amp`) are removed while the other parameters keep their order and encoding; the address that the Google amp viewer (`google.com/amp/s/...`) or the amp cache (`*.cdn.ampproject.org/c/s/...`) wraps around a page is unwrapped and checked again; and an address that ends in a quotation mark (straight, curly or a guillemet), an angle bracket or an apostrophe is refused as `bad_address`, because nobody can open it and a site that answers it anyway answers with its landing page. A host called `m.` or `amp.` and a path that ends in `/amp` are **not** rewritten by guess: a guess can name another site (`m.media-amazon.com`) or another page (a product called Amp).

A page says what its own address is, and `acceptCanonical` takes that claim (`<link rel="canonical">`, else `og:url`) only when it is the same document as the address that was asked for or the one that answered after the redirects: the same site (`www.`, `m.`, `mobile.` and `amp.` and the scheme do not count), the same path (a trailing slash, an index file and an amp form do not count) and the same query. A claim on another site cannot take the address of someone else's page, and a claim on another page of the site (the home page, which a broken template names on every page) or one that drops the parameters that name the page (`?page=2`) is not taken. The entry is then kept under the claimed address and both spellings count as read.

A claim on another site is not taken, but it is kept: `crossSiteCanonical` resolves it like any address and gives it when its site is not the site that answered, and the entry of the page keeps it as `canonicalUrl`. That is how a copy on a portal names the publisher whose story it is. The address is never followed or read; only the [credibility label](../domains/vendors.md#credibility) reads it, to credit the copy to that publisher.

### Reading the page

`pageText.ts` turns the HTML into text with `sanitize-html`, which is already a dependency and reads malformed pages safely. `jsdom` is not used: Jest replaces it with a stub, and it is heavy. `script`, `style`, `textarea`, `option`, `noscript`, `svg`, `iframe`, `template`, `head`, `nav`, `footer`, `header` and `aside` are dropped with their content, block elements become line breaks and whitespace is collapsed. A page that nests tags too deeply is given up on while the parser is still cheap, and at most the first 2 MB of HTML is read.

- **Title and date** come from the raw HTML: `article:published_time` and similar meta tags, JSON-LD `datePublished` and `time[datetime]`.
- **Excerpt.** At most 8,000 characters. Without `focus`, the start of the text. With `focus` (a few keywords), the first 1,000 characters plus the paragraphs with the most keyword hits, in page order, with a visible gap marker (`[…]` on a line of its own) where text is left out. A quote must not span a gap.
- **Parts.** A page that does not fit in one excerpt is also cut into parts of at most 8,000 characters (`pageParts`): the cuts fall at a paragraph, a line or a word past the middle of the window, never inside a surrogate pair, and the whitespace at a cut is dropped. At most 40 parts are made (about 320,000 characters); the rest of a longer page is not offered. The result of a read says how many parts the page has, and the model reads the same address again with `part` (from 1 to the number of parts) to see another one. The session holds the text of the pages it has read (`heldPages`), so a part comes from memory: it is not a request, it takes nothing from the budget of page reads and it has no call record. A part of a page that was not read, or a number outside the parts, is refused with a reason. The first 2 parts that the model asks for are kept as sources: they are merged into the ledger content of the page behind a gap marker, and later parts are shown but not kept, because the model is shown only what the evidence holds, so that a quote it takes from a part is a quote the validation can find.
- **Links.** For a page on the vendor's own domain, at most 25 links to that domain whose text or path contains a security, trust, privacy, legal, terms, subprocessor, compliance, certification, GDPR, cookie, status, incident, vulnerability or disclosure word, or the word AI, DPA, SOC or ISO, so that the model can move from the home page to the right pages. A link whose URL is longer than 2,048 characters is left out: the model could not read it.

### Reading a PDF

Data processing agreements, SOC 2 letters and security white papers are often PDFs, and a research that cannot read them misses the documents that matter most for the AI-specific and certification categories. `readPage.ts` reads a PDF in these steps:

1. **The fetch is the guarded fetch** (URL and address policy, `robots.txt`, redirects), asked for pages and PDFs. `application/pdf` and `application/x-pdf` are allowed for every address. A server sometimes sends a PDF as an unknown file, so `application/octet-stream` and `binary/octet-stream` are allowed too, but only for an address whose path ends in `.pdf` (the query does not count), and the file is read as a PDF only if `%PDF-` is in its first 1,024 bytes; any other file of that type is `unsupported_type`. A body of these types may be 10,485,760 bytes (`maxBytesByType` of `guardedFetch`, counted after decompression, so a compressed bomb is cut as a page is); the 2,097,152 bytes of every other type are unchanged. The bytes are never decoded as text.
2. **The file goes to a worker thread** (`pdfText.ts`, `readPdf`), one thread for each file, which loads `pdf-parse` (already a dependency; the same library reads uploaded files) and answers with the text of the pages, the page count and the title and dates of the document. The thread has a heap of 256 MiB (`resourceLimits`), 20,000 ms from start to answer, and reads at most the first 100 pages; the parent ends the thread when the heap is full (`too_big`), when the time is up (`too_slow`), when the thread leaves without an answer (`unreadable`) and when the caller gives up (`aborted`, which the page reader reports as `unreachable`). The library's evaluation of font programs is off and system fonts are not used. At most 2 files are read at the same time in the process, however many runs are going; the others wait, and a caller that gives up leaves the queue. The worker script is a string run with `eval`, not a file of the build, and the thread makes no request. A thread bounds time and memory; it is not a sandbox, so a flaw in the library would still run with the rights of the server, and the library is kept up to date like the other dependencies.
3. **The text is made readable.** The library gives one line of print on each line, so `reflowPdfPage` joins the lines of a paragraph (a line continues the paragraph unless the line before it stopped short of the width of the page although the first word of this line would have fitted, the line starts a list item or a numbered clause, or the page leaves a blank line; a word broken at a hyphen is joined without a space) and separates paragraphs with a blank line, so that `focus` has paragraphs to pick. A wrong guess changes only where a paragraph ends, and a quote is checked with white space made alike. Ligature glyphs (`ﬁ`) are written as letters and soft hyphens are dropped; nothing else is normalised, because a trademark sign must not turn into `TM` glued to the vendor's name. The text then goes through the cleaning of every page text and is cut at 320,000 characters, the 40 parts of 8,000 that a page can be shown in (see *Parts*).
4. **Title and date.** The title is the document's own, unless it is a name that a program wrote (`Untitled`, `Document1`, `Microsoft Word - ...`, a file name), and then the file name of the address as words (`/legal/Acme_DPA-v3.pdf` is `Acme DPA v3`). The date is the later of the creation date and the modification date, ignoring a date more than a day ahead of the clock and one before 1993 (a program writes 1970 when it has no date); a PDF date is read only with its year, month and day. There are no links and no canonical address.
5. **A PDF with fewer than 40 characters of text** is a scan with no text layer and is not a page (`unsupported_type`; there is no OCR). The reason of any failure is a closed word and the message is fixed, because the text of a failure can hold a path or a piece of the file.

The routine work of the code treats a PDF of the vendor's site as a page of its category (a data processing agreement as `ai_specific`), but reads a page before a PDF of the same fit, because a PDF is the slower read and has no links.

### Rendering a page that a script builds

Some sites send a page of 20,000 characters or more that holds almost no text: the text is built in the browser by a script. Before such a page is given up on as one that `needs_javascript`, the reader tries two things, in this order, and uses the first that gives at least 500 characters of text.

1. **The data the page carries** (`scriptedText.ts`, `extractScriptedText`). Nothing runs. A page that a script builds often holds its text as data, for its first render and for the search engines: the `props.pageProps` of a Next.js page (`<script id="__NEXT_DATA__">`), JSON-LD blocks (`<script type="application/ld+json">`) and `<noscript>` blocks. What is taken out is prose: a string of at least 25 characters and five words that reads as a sentence (mostly letters), and not an address, an identifier, a list of class names, code or the notice that a page needs scripts. A string with markup in it (a content system stores rich text so) is turned into text like a page. The keys that carry addresses, styles and images (`url`, `href`, `src`, `image`, `logo`, `sameAs`, `class`, `slug`, `id`, `query` and the like) are not read. A sentence is kept once, in the order of the page, and the text is cut between sentences at 100,000 characters. The data is written by a third party, so it is bounded: at most 50 data scripts and 50 `<noscript>` blocks are read and none of more than 1,500,000 characters, the data is walked without recursion to a depth of 40, through 50,000 values, and at most 5,000 strings are taken from it, and a page of unclosed scripts costs one scan.
2. **A headless browser** (`renderPage.ts`, `createChromiumRenderer`), only when `VENDOR_RESEARCH_HEADLESS` is `true` (the worker reads it; the default is off, because a browser is the heaviest thing a run does). The page is code of a third party, so the browser runs it on the terms of the guard:
   - **The browser opens no socket for the page.** Every request the page makes is intercepted and either answered by `guardedFetch` (URL and address policy, `robots.txt`, redirects and the limits of any fetch: the bot's User-Agent, no cookies, no credentials) or refused. The document itself is served from the bytes that were read, so it is not fetched twice. Chromium also starts without a way to resolve a name (`--host-resolver-rules`), so what interception cannot see, a preconnect for one, goes nowhere, and without the direct UDP of WebRTC; web sockets are closed. The provenance rule above applies to the page the model asked for, not to the scripts it loads: those are requested through the guard like any other fetch.
   - **Only what a page needs to build its text is fetched**: scripts, and the requests of its scripts for data (`fetch`, `xhr`), by `GET`. Images, fonts, styles, media, beacons and every other kind of request are refused, and so is any request that is not a `GET`: a page of a vendor must not be able to make our server post anywhere. The check that a browser makes before a request to another site (CORS) is answered, and what the guard fetched is handed to the page as readable by any site, because nothing in it is private to the page.
   - **The page cannot go anywhere.** A frame inside it is not opened, a second navigation of the page is answered with "no content" (the browser stays on the page it has; refusing it would replace the page with an error page), a window it opens is closed, a dialog is dismissed, downloads are off, service workers are blocked and there are no permissions.
   - **It is bounded.** At most 60 requests and 12 MiB of answers (3 MiB for each) for a page, and 20,000 ms for the whole render, in which the browser waits at most 6,000 ms for the network to go quiet once the document has loaded, and then 1,500 ms for the page to hold 500 characters of text. After that the context is closed, and a context that does not close within 3,000 ms takes the whole browser with it. At most 2 pages are rendered at the same time in a process, however many runs are going (`limiter.ts`). The browser is started when the first page needs it, kept, and closed after 60 seconds without use. When it cannot be started (no Chromium on the host), that is logged once and it is not tried again for 5 minutes.
   - **The sandbox.** Chromium keeps its own sandbox unless the process runs as root, where it refuses to start with one; then it is started without it, as the PDF reports are (see [PDF generation](pdf-generation.md)). Run the backend as an unprivileged user to keep it. A browser bounds time and memory, and the guard bounds what it can reach; neither makes the code of a page harmless, so Chromium is kept up to date like the other dependencies. The published image contains Chromium (`PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH`).

   The HTML that the browser built goes through the same text extraction as any page, and the title, date, links and canonical address come from it. A failure of any kind (no browser, a page that does not load, the time, the caller giving up, or still fewer than 500 characters) is an answer of nothing, and the page is reported as `needs_javascript` as before. For the model nothing changes: it reads the address as usual.

## The search engine

`search({ query, category, kind })` goes through the `SearchEngine` interface (`webSearch.ts`):

```typescript
interface SearchEngine {
  readonly id: "anthropic" | "openai" | "gdelt" | "replay";
  readonly kinds: readonly ("web" | "news")[];
  readonly newsWindowMonths: number | null;
  search(query: string, kind: "web" | "news", signal?: AbortSignal): Promise<SearchResult[]>;
}
```

`createVendorResearcher` builds the engine of each run after the check of the website, from the `search` spec that `resolveOrgModel` read from the research key (see [Search engines](#search-engines-q21-decided-2026-10-31)); an engine given as `deps.engine` (the tests, the replay of a recording) is used as it is. A GDELT run gets `createGdeltEngine` with the vendor's names, including the other names that the website gave, and the topic words of the news categories and the authorities of the vendor's jurisdiction. An Anthropic run gets `withFallback(withSearchCache(createProviderSearchEngine(...)), gdelt)`: the cache goes around the first engine only, so that the answer of the search that triggers the switch, which GDELT gave, is not filed under the key of the provider. `ResearchResult.searchEngine` reports the engine the searches went to, and the pipeline stores it on the run when a search was answered.

- **Kinds.** `kinds` says what the engine answers: Claude's search `web` and `news`, GDELT `news` only. The web session refuses a search of another kind before it reaches the engine, as `kind_unavailable`: no request, no unit of the budget, no record of a call and no work on the category, and the model is told a fixed phrase ("Web search is not available in this run; search the news or read the vendor's pages"). A search with no `kind` is a web search when the engine answers the web, and a news search when it does not (`defaultKind`). The loop prompt is built for the engine: it describes only the kinds the engine answers, makes the news the default kind when the web is not one of them, and tells the model how far back the news reaches (`newsWindowMonths`, 3 for GDELT), since an event older than that is not in it. A fallback reports the kinds of the engine that answers now.
- **Dropped results.** The engines drop a result whose address does not pass the URL policy and a repeat of an earlier address in the same answer. The session also drops an address that is already in the ledger.
- **Lookback, in code.** A result with a known date older than the window of its category is dropped and counted, and the model is told how many were left out. A result without a date is kept. See [Vendors](../domains/vendors.md#categories) for the windows.
- **Relevance, in code.** A result whose title, snippet and address do not name the vendor never enters the ledger and cannot be read; the model is told how many were left out ("N results did not mention the vendor"), so a search that returns nothing about the vendor is visible as that. The session asks the vendor matcher of `identity.ts`, which `createVendorResearcher` hands it as `isRelevant`; a result on the vendor's own domain is not asked about. The name is matched as a whole word, with and without the legal form that the record carries ("Acme Analytics, Inc." and "Acme Analytics"), the domain is matched as a whole word (`acme-analytics.org` is not `acme-analytics.com`), and the host and path of a result are read as words (`news.example/acme-analytics-breach`). The validation uses the same matcher on the title and the text of a source, but not on the address: the address of a page is the one that was asked for, and the page can answer from somewhere else.
- **Dates.** GDELT dates an article by the day and time it saw it (`seendate`). Claude's search gives no date: the `page_age` of its sources is when the page was last updated, not when it was published, so it is not used, and a result of the web has no date in the ledger, in the model's history or in the evidence. A date of a web result, wherever an engine gives one, is only an upper bound for the lookback (a page is not newer than the day the engine saw it). The page gives its own date when it is read, and the lookback is checked against that after the read.
- **A failed search.** Every failed search comes out as the fixed `SearchEngineError` ("The search is not available right now"), which repeats nothing of the query, the request or the answer, and the model is told so. An answer with no results is an answer: an empty list. Every search step is counted by kind and outcome (`vendor_research_searches_total`: `results`, `empty`, `refused`, `failed`) and every retry of GDELT by kind (`vendor_research_search_retries_total`); see [Observability](observability.md).
- **The query.** The session does not search for what the model wrote: it searches for `normalizeQuery(query, target)` of `queries.ts`, which `createVendorResearcher` hands it as `normalizeQuery`. The result is the vendor's name (as an article writes it, without the legal form of the record) followed by at most three topic words, the first ones the query had. Search operators (`site:`, `inurl:`, `filetype:`, `before:` and the like, with or without a minus), the boolean words `OR`, `AND` and `NOT`, quotation marks, brackets, addresses, small words ("what", "the", "latest", "news"), the words of the vendor's own name and a topic repeated in another case are all removed; a query with no topic left searches for the name alone. The budget, the repeated-query check and the ledger work on the normalized query. When the normalized query differs from what the model wrote, the result starts with "Searched for: <query>" and the trace step keeps both (`query` and `usedQuery`), so the model sees what it really got. The shape was tuned on the Bing feed (probed 2026-10-27: a short query answered best, `site:` was not understood) and stays until it is measured on the new engines. The loop task also lists the queries that work for the four news categories (`suggestedQueries`: "<name> data breach" and "<name> security incident" for `security_incidents`, "<name> lawsuit" and "<name> fined" for `legal_regulatory`, and for a vendor with no market of another language the name with the authority of its country and `settlement` as well, see [The regulator in the query](#the-regulator-in-the-query), "<name> outage" for `availability`, and "<name> layoffs", "<name> bankruptcy" and "<name> acquisition" for `financial_health`); the categories that read the vendor's own website get none.

**Claude's search** (`providerSearch.ts`). Each search is one `generateText` call with the `web_search_20250305` tool (`maxUses: 1`, `tool_choice: auto`), fixed instructions that relay one search ("call `web_search` exactly once with the query the user gives, do not answer the query") and a prompt that holds the query as a JSON string on a line of its own, so that whatever the query contains stays inside the quotes; at most 200 output tokens, no SDK retry, and the abort signal of the search. Before the call the query is cleaned to one line of 200 characters at most; a blank query or an aborted signal makes no call. Four searches run at the same time for an engine (`createLimiter(4)`). The results are the `url` sources of the reply, each address through `parsePublicUrl` and once, at most 10, in the provider's order; the title is the source's title (else the host and path), the snippet is empty and there is no date. A search ran when the reply holds a result of the `web_search` tool; an error result of the tool (`too_many_requests`, `max_uses_exceeded`, `unavailable` and the others), a reply with no search, any thrown error (429, 5xx, 401, 403, network) and an abort are failed searches. The API answering 400 or 404 means that the key cannot search (the tool or the model is not allowed, or web search is turned off for the organization): that is a `SearchUnavailableError`, and `withFallback` moves that search and every later one of the run to GDELT. Any other failure is an ordinary failed search and the next search goes to Claude again. The fee is about $10 per 1,000 searches plus the tokens of the call, so the daily cap bounds the cost; each call is a `purpose: "search"` model call in the trace with its tokens.

**The news of GDELT** (`gdeltSearch.ts`). The module comment is the full account; the rules in short:

- **One request for a run.** GDELT has no cheap way to ask for the news of one topic, and a run makes about 20 to 30 searches at 5 seconds apart, so the engine makes ONE request for the run, the first search's: `GET https://api.gdeltproject.org/api/v2/doc/doc?query=("name" OR "other name") AND (topic OR "topic phrase")&mode=artlist&format=json&maxrecords=250`, through the guarded fetch with the bot's User-Agent, 20,000 ms and at most 1,048,576 bytes. The names are quoted as the press writes them, without the legal form; the topics are the English topic words of the news categories and the authorities of the vendor's jurisdiction. The first 250 articles that are articles, each address once, are the run's index, and every search of the run is answered from it in code: the articles whose title names a topic word of the query (at the start of a word) or are not in English (GDELT matches its machine translation, so a title in another language cannot be tested for an English word), newest first, ten at most. `timespan` is never sent (it made GDELT answer `{}` to queries that do have matches); the window of the API without it is the last 3 months. Searches that run at the same time share the one request.
- **The index is cached.** The index of a request is kept for an hour in the cache that runs share, under the address of the request, so that a second run of the same vendor makes no request; it is public data that the GDELT terms let anyone redistribute. The engine is not wrapped in `withSearchCache`: it caches what it asked, not what it was asked.
- **`robots.txt`.** `api.gdeltproject.org/robots.txt` is a 404 (checked 2026-10-31), so nothing is disallowed, and it is asked all the same, as the page reader asks the site of a page, and the answer is kept like any other. It is asked with the time limit of the request itself (20,000 ms) and not a shorter one: on 2026-11-01 the TLS handshake with the API host took 6 to 10 seconds from the golden machine, and a `robots.txt` that cannot be fetched in time disallows everything (RFC 9309, 2.3.1), which cost every run all of its news.
- **The rate and a 429.** GDELT asks for one request every 5 seconds from an address. All the engines of the process share one queue that spaces requests 5,000 ms apart (`GDELT_MIN_GAP_MS`). A faster client gets a 429 with a plain-text body and no `Retry-After`, and kept getting it 25 and 50 seconds after a burst. After a 429 the process leaves GDELT alone for 60 seconds (`GDELT_COOL_DOWN_MS`): a search that would need a request in that time fails at once, with no request. The refused request is not given up for the rest of the run: the first search of the run that needs it after the pause asks it again, and when GDELT answers, that search and the later ones of the run are answered from the one index. A run asks at most `GDELT_MAX_ASKS` = 3 times: once GDELT has refused the run's asks 3 times, the searches of the run fail at once. Only a 429 is asked again this way and only a 429 counts towards the cap; a refusal is never cached, an answer is. On 2026-11-01 GDELT refused 11 of 12 requests from the golden machine at intervals of minutes, and in one probe refused a request and answered the next one 6 seconds later, so the refusals do not come from our own rate, and a single 429 must not cost a run all of its news.
- **Other failures.** A network error, a time-out and a 5xx are asked once more through the queue, after the `Retry-After` of the 5xx when it asks for 5 seconds or less; a 4xx other than 429, a refusal of the URL policy or of `robots.txt`, a type that is not JSON and a body that is not an index are not asked again. A query GDELT refuses (too short, badly formed) is answered with plain text and a 200 and a rate limit with plain text and a 429; neither is JSON, and neither is read as an answer. `{}` is an answer: nothing was found.
- **The body is third-party text.** It is read with `JSON.parse`. The clients of this API are known to meet two flaws in a body that is otherwise an answer, a raw control character and a backslash that begins no escape, both in a title; `JSON.parse` refuses the whole body for either, so a body it refuses is repaired once, by two passes of fixed-width patterns (a control character becomes a space, a stray backslash is escaped) and read again with `JSON.parse`; whatever is still refused is no answer. No other pattern is run over the body. Every address must pass the URL policy, a title is one line of plain text cut to the length of a snippet, and no more than 250 entries are read. Nothing is logged here: the query is never written anywhere.

## The research loop

`runResearchLoop` (`researchLoop.ts`) asks the model for one step per turn as a JSON object: a `thought` and a list of `actions`, up to four. Each action has an `action` (`search`, `read` or `finish`) and, as that action needs them, `category`, `query`, `kind`, `url`, `focus` and `part`. An answer in the older form, with one action in the step itself, is read as a step of one action. It uses the self-correcting structured call and not native tool calling, so it runs on every model that can answer the app's other structured calls (OpenAI, Anthropic, DeepSeek, custom endpoints, local models). A model that cannot answer in JSON fails the run with a clear message.

Each prompt carries the task (the vendor, today's date, the categories and their lookback windows), the history of the steps and the budget that is left. The results of the two latest steps are shown in full, whatever the number of their actions, and older ones are cut to 500 characters, because the ledger keeps the full text for the analysis. Everything in the history, results and the model's own words alike, is escaped with `escapeForPrompt`, so none of it can close a tag of the prompt or open a new one.

**Several actions in a step.** A step is one model turn however many actions it holds, and a model turn costs two to three seconds where a search or a read costs a fraction of that (see *Why these limits* below), so a model that puts the actions that do not depend on each other in one step saves turns. The loop runs the first four actions of a step in order (`MAX_ACTIONS_PER_STEP`). An answer may hold up to 16 (`MAX_ACTIONS_IN_ANSWER`) so that a model that asks for too many costs a step and is told how many were left out (`too_many_actions` in the trace), not a round of self-correction. The reads that follow one another go to the web together through `session.readMany`: they are checked one after the other in the order of the step (the budget goes to the first, and an address asked for twice is read once, also when two calls ask at the same time), fetched at the same time (at most two at once from one host, so a site is not asked for a crowd of pages), and settled in the order of the step, so that the ledger, the refunds and the same-text rule come out the same whichever page answered first. A search, and a read next to a search, is not run at the same time as the action before it or after it. A `finish` ends the research once the actions before it have run (the first `finish` of a run still gets the reminder when something is missing), and the actions after it are not run. When the loop's time is up, the actions that have not started are not started. Each action is one turn for the observer and one step of the trace; they share the `turn` of the model turn, and only the first carries the thought.

**The check of the website.** Before the first step, `createVendorResearcher` reads the vendor's home page once (`https://<domain>/`, through the run's own page reader, so the `robots.txt` rules and the address policy apply) and tells the model what it found, in a `<briefing>` block between the task and the history. The block is shown whole in every turn, is escaped like a result (it holds the page's link texts), and is data like a result. The read happens outside the session: it uses none of the 12 reads, leaves nothing in the ledger, and is not a call of any category, because a home page is where the useful pages are linked and seldom a source in itself. The answer is one of four kinds:

- **Readable.** The page was read. The briefing says whether it names the vendor (by the vendor's name, with or without its legal form, as a whole word in the title or text; never by the domain, which a parked page repeats), and, when it does and stayed on the vendor's site, lists up to 12 of its links to security, trust, privacy, legal, compliance and similar pages, so that the model can read them directly instead of reading the home page first. A page that does not name the vendor gets a warning that the website may belong to another company (a typo in the record, a parked domain) and no links; that changes nothing in the session. A page that redirected off the vendor's domain says where it went. When the page it landed on names the vendor **and** the domain has the brand of the recorded one (`notion.so` to `www.notion.com`, `acme.com` to `acme-analytics.com`; the brand is the label before the suffix, `co.uk`-style suffixes included, at least three letters, one holding the other), the site **moved**: the landing domain (without `www.`) is an **alias** of the vendor's website and the session gives it the standing of the recorded domain (`aliasDomains`): its pages and those of its subdomains are read without a search, are marked as the vendor's own, are exempt from the lookback and are not asked about relevance, and the briefing lists its links. A redirect to a domain of another brand (a social page, a host of many sites, a page that does not name the vendor) is only reported, and the pages there are "not the vendor's own". The trace says which: `redirected_to_alias` or `redirected_off_site`.
- **Unreadable.** The site answers but its home page is no use: it does not exist, is not a web page, or is built by a script and holds no text. The briefing says so and that other pages may exist. Nothing is closed.
- **Closed.** The site does not answer (the bare domain and then its `www.` form are tried, because a site with no record for the bare domain is not closed), its `robots.txt` disallows the home page, the site refuses the request (401, 403, 429), or the address policy refuses the host. The session is created with the bare domain and its `www.` form as `closedHosts`: a read of a page on either is refused as `site_closed`, with no request, no unit of the budget and no record of a call, so a dead site is not tried once for every page the model thinks of. The subdomains are not closed (a trust center on its own host can answer when the main site does not). The briefing tells the model to research with searches. The categories that need the website (`certifications`, `ai_specific`) that the model made no call for are recorded as reads that failed, so the run summary says "The pages could not be read" and not that the research ended before it got there; a category the model worked on by a search keeps the outcome of that work.
- **Unchecked.** The check itself broke (the reader threw something that is not a failed read). The run goes on as if there were no check.

The whole check has 25,000 ms. A vendor without a domain has no check and no briefing. The check is the first step of the [trace](#the-run-trace) (`tool: "preflight"`, with `reason` `does_not_name_vendor`, `redirected_off_site`, `redirected_to_alias`, `check_failed`, or the failure of the read).

**The routine work before the first step.** Every run began with the same model turns: the news searches, the reads of the best results, and the reads of the vendor's trust, security, privacy and legal pages, at two to three seconds a turn (see *Why these limits* below). With `gather: true` (the job turns it on; the evaluation turns it on for the cases that say `gather: true` and for live runs) `createVendorResearcher` has code do that work (`gather.ts`) after the check of the website and before the first model turn, in at most 30,000 ms (`GATHER_TIMEOUT_MS`):

- **The searches.** The queries of `suggestedQueries` (the vendor's name and one or two topic words: `data breach`, `security incident`, `lawsuit`, `fined`, `outage`, `layoffs`, `bankruptcy`, `acquisition`; for a vendor with no market of another language, two for the authority of its country as well, searched with the legal news: `Acme FTC`, `Acme settlement` (see [The regulator in the query](#the-regulator-in-the-query)); for a vendor with other names, one more query for each news category, led by its first other name: `Facebook data breach`; for a vendor in a market of another language, two more for each of `security_incidents` and `legal_regulatory` in that language: `Brume Logiciels CNIL sanction`) for the news categories the run can use, and the searches that the hints make (below), through `session.searchMany` (two at a time). The task of the loop then no longer lists the queries that work: the briefing says what was searched.
- **Hints from the model's memory.** One cheap model call, started while the website is checked, asks for one more search query for each news category (at most four) about an incident, a legal matter, an outage or a financial matter the model remembers for this vendor (`hints.ts`; 15,000 ms; no self-correction; the call is in the trace as `purpose: "hints"`). Its answer is only ever a query: it is made the shape the feed answers best (the vendor's name and at most three topic words), dropped when it has no topic word or repeats a baseline query, and searched with the others. It is never put in the ledger or told to the loop as a fact, its prompt holds no web content, and a hint that is wrong finds nothing that names the vendor. A model that fails or is late gives no hints and changes nothing else. The call also learns whether the provider rejects `json_schema`, so the loop can start in JSON-object mode.
- **The articles.** Once the searches are in the ledger, the best two results of each news category are read in full (`planNewsReads`), because a snippet is short and can mislead. A result is better when its title names the vendor, then when its source is better (by the registry category of its host: official sources first, then trusted press, then the vendor's own site, then unverified hosts, an aggregator or a forum among them; see [Credibility](../domains/vendors.md#credibility)), then when it is more recent (an undated one last), and last by its place in the search. Results of different publishers come before a second one of the same publisher, since two independent publishers are what a confident finding needs. The page is read around the vendor's name (the `focus` of `read`), so a long page is read where it speaks of the vendor. The model's own searches later in the loop are not read by the code: the model chooses what to read.
- **The vendor's pages**, for the categories that read the vendor's site (`certifications`, `ai_specific`): the pages the home page links to and the pages `/sitemap.xml` lists, ranked by the words of the address and of the text of the link (`trust`, `security`, `compliance`, `soc 2` for certifications; `subprocessors`, `dpa`, `privacy`, `ai`, `terms` for `ai_specific`; blog, news, press, career pages and files are no candidates). Links come before the sitemap, and a shallower path before a deeper one. At most three pages are read for a category. A category left with fewer than two candidates gets the pages that sites usually have: `/security`, `/trust`, `trust.<domain>`, `security.<domain>`, `/compliance` and `/.well-known/security.txt` for certifications; `/privacy`, `/legal/privacy`, `/privacy-policy`, `/terms`, `/legal/dpa` and `/subprocessors` for `ai_specific`. Nothing is a guess about the vendor: the pages are on its own site, and a page that does not exist is a failed read like any other. The sitemap is read outside the session, like the home page: it is a list of addresses, so it uses no budget and leaves nothing in the ledger. Its markup is kept raw (the text of a page would glue the addresses together), and a sitemap index is not followed.
- **The records of public databases**, for `security_incidents`, `legal_regulatory` and `availability`: the code looks the vendor up in the CISA catalog of known exploited vulnerabilities, the National Vulnerability Database, Have I Been Pwned and the filings of the SEC (security incidents) and in the sanctions list of the United States Treasury (legal and regulatory matters), and reads the incident history on the status page of the vendor (availability); see [Records of public databases](#records-of-public-databases). The lookup is started first, so that the databases answer while the sitemap is read, and each record that matches is put in the ledger as a source that was read, in the category of its database, before the searches are made, so it comes first among the sources of its category. It costs no search, no read and no model turn, and it is not a call of the category.
- **When the site is not read.** The site is skipped when it is closed, when the home page redirected somewhere that is not the vendor's website, and when the home page does not name the vendor (the domain may be another company's). The searches are made all the same. A vendor without a domain gets the searches of the four news categories only.

The reads of the articles and those of the site are sent together (`readMany`, two at a time from one host), the pages of the site first. The work goes through the run's session, so every rule of the session applies to it (the address policy, `robots.txt`, the lookback window, relevance, one entry for one page), but it is paid for apart: `session.setCodeBudget` grants exactly the searches and the reads that were planned, and the calls are made `by: "code"`. The model keeps its own 8 searches, 12 reads and refunds, and a read that failed by code gives nothing back. `searchesUsed` and `pagesRead` of the run count both. The results and the pages are in the ledger, and the calls are calls of their categories, so a category the code worked on is not reported as not reached, and the model's first `finish` is final once every category has a call and the ledger is not empty. The model is told in the `<briefing>`: the searches that were made and how many results each had, how many of the pages of the site and of the articles were read, and up to six sources per category (title, address, date, result or page); the loop prompt tells it not to repeat that work and to use its steps for what is missing.

In the [trace](#the-run-trace) the read of the sitemap is a step with `tool: "gather"`, and every search and read of the code is a step with `by: "code"` and no `turn`. The searches are counted by the same counter as the model's, and the run reports its progress once after the work, as step 0. A `gather` that is off (the default of `createVendorResearcher`, and every replayed case that does not say `gather`) changes nothing: the model does all the work, as before.

**One loop for each category.** With `perCategory: true` (the job turns it on, with `gather`; the evaluation turns it on for the cases that say `perCategory: true` and for live runs) `createVendorResearcher` runs one loop for each category that the vendor allows, all at the same time, after the routine work (`loops.ts`), instead of one loop of 24 steps for all of them. The model turns of one loop cost two to three seconds each and wait for each other, so the loops of the categories take their turns side by side:

- **A budget of its own.** Each loop works through `session.pool(...)`, a view of the run's session that shares the ledger, the records and every rule, and has a budget and refunds of its own, so that a category that needs many pages cannot use up the budget of another. The model's 8 searches and 12 reads are split between the loops (`loopGrants`) and the run costs what one loop cost: each category of the vendor's website (`certifications`, `ai_specific`) gets one search (`SITE_LOOP_SEARCHES`: the web feed answers a topic badly) and the four news categories share the six searches that remain (2, 2, 1 and 1 in the order of the categories: `security_incidents` and `legal_regulatory` two, `availability` and `financial_health` one), and the 12 reads are shared out evenly (2 for each of the six categories); a vendor without a domain has four loops, with 2 searches and 3 reads each. A pool gets half its reads (rounded up) back for pages that failed and one for a page whose text its category already had. The grants are cut from the model's budget before any loop starts.
- **Four turns, and a task of its own.** A loop has at most four model turns (`CATEGORY_LOOP_STEPS`), each of up to four actions, and the same limits of time as the single loop (60,000 ms a turn, 300,000 ms for the loop). Its task names the one category it researches and says that other researchers cover the others at the same time (`You research one category only: <category>.`; `loopScopeOf` reads it back, for the evaluation); the system prompt tells the model what to do when the task names one category. The `<briefing>` holds what the code collected for that category only (the searches and the sources of the category, `describeGathered(..., [category])`), and for the two categories of the vendor's website also the answer of the check of the website; the loops for the news do not need the links of the home page.
- **A finish.** A loop counts only the sources and the calls of its own category when it decides whether its first `finish` still needs the reminder. With `allowEmptyFinish`, which a run that did the routine work sets, calls of its own that found no source are an answer (the briefing says what was searched), so a loop for the news that the code searched and found nothing for finishes at its first turn. A loop that has no call of its own, because the code could not read the site, is reminded once (`You have no sources yet`), like a single loop.
- **The ending of the run.** `combineEndings`: the run was stopped by time if any loop was, otherwise by steps if any loop used its four turns without finishing, otherwise by the budget if any spent it, otherwise it finished. It is a model error only when every loop failed, with the error of the first (the others went on, and what the failed loop gathered is kept). Every loop is waited for, also when one of them breaks (a bug of the session): the researcher rejects after all of them have ended, so that none is left to work behind a run that has been given up.
- **Trace and progress.** Every step and model call of a loop carries `loop` (its category), and the turns of each loop are numbered from 1; the check of the website, the work of the code and the call for hints carry none. The progress reports the sum of the latest turn of each loop as `steps`, which never goes down.
- **Cost.** A loop of one category sends the system prompt (about 1,400 tokens) on every turn of its own, so the tokens of the loops grow with the number of turns of all of them (the evaluation case `one-loop-per-category` counts 8 loop calls and about 18,600 tokens against 3 calls and 5,500 tokens for `gathered-sources`, which does less); the time of the research is that of the slowest loop, four turns at most. The prompt of the loop could be shortened for a loop of one category if the tokens matter more than they do now.

A `perCategory` that is off (the default of `createVendorResearcher`, and every replayed case that does not say `perCategory`) runs the one loop of 24 steps, as before.

A model that answers badly cannot crash the loop or keep it going. An action that breaks its rule (a `search` without a query, a `read` without a URL, an unknown or unavailable category) is answered with the reason, and the other actions of its step still run; a step with no action costs the step. An action that the rules refuse (a budget that is spent, an address that is not allowed or ends in a quotation mark, a page that no search returned, a page on a site that was found closed before the run, a query that repeats an earlier one) never reaches the web. Three answers in a row that hold no step end the loop as a model error. A `finish` before any source is in the ledger, or before every category has a call, is answered once with a reminder; the second `finish` is final.

The loop ends when the model finishes, when both budgets are spent, when the steps or the time run out, or when the model fails. The loop only collects: it never writes findings. What it leaves is the ledger, and a loop that ran out of time or failed with entries still hands its partial ledger to the analysis. A search or a read that the loop's clock cuts off keeps its unit of budget but is not recorded as a failed call: the time ran out, not the web, so the summary says that its category was not reached.

What it decided: the budgets of searches (8), reads (12) and steps (24) stay, since a run ends at its budget in every case and the steps are not what stops it. The reads that failed are given back (above): without it, a site that refuses most of its pages used the budget on refusals. The searches that find nothing in the lookback window are an answer (Twilio: seven of eight searches found no news inside 24 months, which is true), so the loop prompt now tells the model to move on after two empty searches of a category. And the unknown vendor ended in 20 seconds with no source and no analysis, where it took 51 to 57 seconds and 45 unrelated sources before the relevance rule.

**The ledger.** Every snippet and every excerpt goes to a ledger with one entry per URL: `{ category, kind: "result" | "page", onVendorSite, url, title, content, publishedAt }`. Reading a page replaces the snippet of the same URL with the excerpt, keeping the title; the date is the page's own when it has one, and the snippet's otherwise. `onVendorSite` is decided on the URL that answered, so a page that redirected off the vendor's domain is not the vendor's own, and one asked for elsewhere that answered from the vendor's site is. The analysis prompt marks `site="vendor"` from that flag alone, and so does the validation of the findings (the vendor's own page counts as mentioning the vendor); neither reads the host of the URL that was asked for. A page that proves older than the lookback window of its category is refused and kept out of the ledger under that category. Pages on the vendor's own domain are exempt from the lookback. A second read of a URL changes nothing. A `read` with `part` is not a second read: it is taken from the text that the session holds, and the part is added to the content of the page's entry behind a gap marker (see *Reading the page*).

**A read that failed** gives its unit back, at most six times a run: it added nothing to the evidence, and the live traces of 2026-10-27 (see below) had sites that refuse most of their pages using 7 and 9 of the 12 reads on failures. The call is still recorded as one that the web did not answer, so the category outcomes are unchanged. A page that failed for a reason that does not pass (`not_found`, `blocked_by_site`, `blocked_by_robots`, `unsupported_type`, `needs_javascript`, or a refusal of the address policy) is not tried again: a second read of it is refused as `already_failed`, without a request. A page that did not answer (`unreachable`) may be tried again, since a site that is down can come back. A read that failed because the run's own clock cut it off keeps its unit and is not remembered.

**A query that repeats an earlier one** is refused (`repeated_query`) without a request, a unit of the budget or a record of a call. Two queries are compared by their words (letters and digits of any script, lower case, a plural taken for its singular, as sets) and are a repeat at a Jaccard similarity of 0.8 or more, for the same kind (`web` or `news`) and whatever the category, since the engine gives the same answer: "Acme data breach" and "breaches, Acme data" are one query, and so is a five-word query with a sixth word added. A search that failed is not an answer and may be asked again; one that found nothing is an answer. The model is told to use other words, or a read.

**One page, one entry.** The ledger is keyed by canonical address (see [Provenance](#provenance)), so the tracked and the plain address of an article are one entry. A page whose text is the text of a page already read for the same category (compared without regard to case and spacing, and only for 80 characters or more, so that two error pages stay two answers) is not a second source: the read is answered `same_text` with the address of the first, the snippet of the repeated address is dropped, and the read is **given back** (at most three times a run, so that a model that keeps asking for copies cannot read for ever). The call still counts as an answer of the web. A search result whose title and snippet are those of an earlier result of the same category (at least 60 characters of snippet; the same snippet under another title is a site-wide description, not a copy) is left out and counted, and the model is told how many. A result whose address cannot be opened is left out and counted, without a word to the model. Both counts are on the step of the [trace](#the-run-trace) (`omitted`) and in `dropped` (`source.duplicate`, `source.bad_address`, `source.same_text`).

**The JSON-object fallback.** If a provider rejects `json_schema` (DeepSeek does), the call falls back to JSON-object mode. The loop then keeps that mode for the rest of the run, so that each step does not cost a rejected request; a call that fell back and then failed counts too, because the call says so as it falls back (`onJsonObjectFallback`). The run reports what it learned (`jsonObjectFallback`), and the analysis call then starts in JSON-object mode as well.

**From the ledger to the analysis.** `buildEvidencePack` cleans the entries (control characters, lone surrogates, unusable URLs), drops a repeated URL, and numbers the sources `S1`, `S2`, ... after trimming. Until the pack is at most 100,000 bytes, the last source of the category that holds the most bytes among those with two or more sources is removed (a tie goes to the later category). A category with one source keeps it; when every category is down to one, the content of the largest source is cut instead. So a category the loop researched always has a source in the pack, and the summary cannot read it as "nothing found". The analysis, its validation and the run summary are described in [Vendors](../domains/vendors.md#vendor-research-agent).

**The check after the analysis.** The validation holds a quote to the snippet it cites, which proves that the model copied the snippet right and nothing about the page: a snippet is what an engine cut, joined or reworded from a page. So the researcher hands its page reader on (`ResearchResult.readPage`: the same reader, with its `robots.txt` rules and the guarded fetch), and `analyse` uses it, once the caps have left at most eight findings, on every finding whose cited sources are all search results (none of them a page that the research read; `verifySnippets.ts`):

- The most credible cited source is read first (by its registry category: official, trusted press, the vendor, unverified; of equals, the one the model cited first). A page that cannot be read (the site refuses, it is gone, the time is up) gives way to the next source, up to two pages for a finding, and the first page that can be read gives the verdict. A page is read once, however many findings cite it.
- A page that holds the quote **confirms** the finding, which is stored exactly as it was. The quote is compared as the validation compares it (case, spacing and quotation marks ignored); a quote with a gap mark of the engine in it (`…`, `...`, `[…]`) is held when every part between the marks is on the page.
- A page that does **not** hold the quote marks the finding `snippet_only` (a column of the finding), and the credibility rule calls the source contradicted, so the finding's label is `low`: the search result said what the page does not. The finding is kept, never dropped.
- When no page can be read, the finding is marked `snippet_only` and its label stays as the rule gave it (capped at `medium`): nothing was found against it, but nobody has seen the page either. The findings list tells the person ("Not confirmed on the page. The quotes come from search results.").
- All the reads share one deadline of 20,000 ms. The check never rejects: a reader that throws is a page that cannot be read.

**The verifier.** What code cannot read is meaning: a source can name the vendor and be about another company of the same name, a quote can be in the source and say less than the claim states, and a source with no date can be older than the window of its category. With `verifier: true` (the job turns it on, with `gather` and `perCategory`; the evaluation turns it on for the cases that say `verifier: true` and for live runs) `analyse` makes one more model call over the findings that stay, with the model of the analysis and at the same time as the reads of the check above (`verifier.ts`). The prompt holds the vendor and, for each finding, the claim, the impact and the address, date, title and quote of each source it cites, and the windows of the categories; the model answers three questions with true or false (`same_company`, `quote_supports_claim`, `source_in_window`) and is told to answer true when it cannot tell. A finding with a false answer is not kept, and the trace says which question it failed (`verifier.other_company`, `verifier.not_supported`, `verifier.out_of_window` in `dropped`, and a rejection with the start of the claim); a finding that fails several is counted once, under the first. A finding with no verdict is kept: only an answer takes a finding away. The call never fails a run: a model that does not answer within 30,000 ms, or answers badly, keeps every finding, and the call is recorded as failed (`purpose: "verifier"`, `ok: false`) without its error message. A category whose findings were all taken away shows the same note as one whose findings could not be verified.

## The names a vendor is known by

The record of a vendor holds one name, and the press often writes another ("Meta Platforms" is "Facebook" in an article). A source that names the vendor only by that other name would be taken for a source about someone else, and a search that asks for the recorded name only would not find it. So a target (`ResearchTarget`, `target.ts`) can carry **other names** (`aliases`), and the matcher of `identity.ts` reads each of them like the name itself: as written, and without the legal form. They come from two places.

- **A person.** The *Other names* field of the vendor's record (`vendors.other_names`, see [Vendors](../domains/vendors.md#other-names)): names separated by commas, semicolons or line breaks, trusted as they are. `parseOtherNames` removes control characters, collapses white space, passes over a name of fewer than 2 or more than 80 characters or with no letter or digit in it, keeps a name once however it is written (`Face-Book` is `Facebook`) and keeps at most 8. These are the limits that the record is validated with (`VENDOR_VALIDATION_LIMITS.OTHER_NAMES`), so a name that a person can save is a name that the research keeps. `buildTarget` puts them on the target.
- **The vendor's home page.** What the page says about itself, adopted under the rules below. A page is the claim of a third party, so its names come after the person's and are held to more.

**What a page says about itself** (`siteIdentity.ts`, `extractPageIdentity`). The page reader reads it from the HTML of every page it fetches (also a page that the headless browser built), and nothing is run. The names come from the meta tags `og:site_name` and `application-name`, from the JSON-LD nodes of an organization type (`name`, `alternateName`, `legalName`) and from those of a `WebSite` (`name`, `alternateName`); the products come from the JSON-LD nodes of type `Product`, `SoftwareApplication`, `WebApplication`, `MobileApplication` and `Service` (`name`). Only the fields of the node itself are read: an organization that a node names inside itself (a parent, a member, a brand) is not the name of the site. A name is a text of 2 to 80 characters with a letter in it that is not an address, markup or a tagline (`Acme | Cloud hosting for teams`). A name is kept once whatever its case, and at most 8 names and 12 products are kept. The reading is bounded like the other data of a page: at most 200 meta tags, 500 nodes in a JSON-LD block and 4 levels of `@graph` and lists, and the blocks themselves are those that `scriptedText.ts` finds, within the same limits. The result is the `identity` of the fetched page, set only when the page says something. The shared cache keeps it with the page; an entry written before the field existed has none, and one with a malformed identity is a miss.

**Which names the research adopts** (`aliases.ts`, `profileOf`, called by `checkWebsite` for the home page).

- Only when the page **names the vendor and is the vendor's own** (the recorded domain, or the domain it moved to, see *The check of the website*). A page that does not name the vendor, or that redirected to another site, gives no names: the domain may be another company's.
- A name is adopted when it is **built around the vendor's brand**: it holds the first word of the vendor's name (without the legal form) or the brand of its domain (`facebook` for `facebook.com`), a brand of at least 3 letters. A name that is only a part of the recorded name (`Analytics` for `Acme Analytics`) is left out, because other companies use it too, unless it is the brand of the vendor's domain (`Acme` for `acme.com`). A name the vendor already has (its own, without the legal form, or one a person wrote) is not added again. At most 4 names are adopted.
- **Products are never names** (`Windows 11` does not make a source about Microsoft). At most 5 go to the briefing only, which then says "The site gives these names for itself: …" and "It lists these products: …".

**Where the names are used.** `checkWebsite` returns the adopted names as `WebsiteCheck.profile` (`siteNamesOf`), and `createVendorResearcher` builds `known = withAliases(target, siteNames)`: the person's names first, then the site's, at most 8, none that repeats the vendor's name. `withAliases` gives the same object back when it adds nothing, so the matcher that is kept for a target (`identity.ts`) is not built again. `known` is the target of everything after the check:

- **The matcher of the session.** A result or a page that names the vendor by one of its other names is about the vendor.
- **The queries** (`queries.ts`, `hints.ts`). `normalizeQuery` reads an other name as the vendor's name: a query that names the vendor only by an other name keeps that name as its lead (the domain is taken out first), and when the query leads with the vendor's name, an other name stays a topic word. `suggestedQueries` adds one query for each news category with the first other name and the first topic word (`Facebook data breach`), and `hintSearchesOf` drops a hint that is only an other name.
- **The routine work** (`gather.ts`). The articles are read with the name and the other names as `focus`, so the excerpt keeps the paragraphs that hold any of them, and a result whose title names the vendor by an other name ranks as one that names the vendor.
- **The prompts** (`prompts.ts`). The task of the loop, the call for hints, the analysis and the verifier carry the names as `<also_known_as>`, the system prompts say that a source may name the vendor by any of them, and the briefing says what the site calls itself.
- **The analysis.** `ResearchResult.siteNames` hands the adopted names to the pipeline, which calls `analyse` with `withAliases(target, found.siteNames)`. The validation (a citation of a source that is not about the vendor is refused), the verifier and the prompt of the analysis therefore use the same names as the search did, and a source the search let in by an other name is not refused for being about someone else.

The [trace](#the-run-trace) is unchanged. It records no names, because a page wrote them and the closed schema holds no text that a third party wrote.

## The news in the vendor's language

A news search answers a query in the language it is written in, and the press of a vendor in Germany, France or Italy writes in German, French or Italian first: the data protection authority of the country tells what it fined in its own language, and the English press reports only the larger cases. So for a vendor whose market is known, the news categories are searched in that language as well (`market.ts`).

- **The market** is read from the vendor's record and from nothing else (`marketOf`): the country stated for the vendor (a stated US, GB, IE or AU means no market, whatever the domain and the legal form say; a country no table holds changes nothing), else the country domain of its website (`.de` and `.at` are German; `.fr`, `.it`, `.es`, `.nl` and `.pt` French, Italian, Spanish, Dutch and Portuguese of Portugal; `.br`, as in `.com.br`, Portuguese of Brazil), else the legal form at the end of its name (`GmbH`, `AG`, `UG`, `KG` German; `SAS`, `SASU`, `SARL` French; `S.r.l.`, `S.p.A.` Italian; `S.L.`, `SLU` Spanish; `B.V.`, `N.V.` Dutch; `Lda` Portuguese of Portugal; `Ltda` Portuguese of Brazil; the letters are compared, so `S.p.A.` is `spa`, and a name of one word has no legal form). A country domain wins over a legal form. A domain such as `.com`, `.io` or `.ch` says nothing of where a company is, and neither does a legal form that exists in several countries (`S.A.`) or in English (`Inc.`, `Ltd`), so a vendor like that has no market and is searched in English only. The language of the vendor's pages is not read.
- **The queries** (`localQueries`) are two for each news category that has them (security incidents and legal and regulatory; the outage news is searched in English only, for every market): the vendor's name without its legal form and then the words of the market. The first is about the breach or the incident (`Datenleck`, `Cyberangriff`; `fuite de données`, `cyberattaque`; `violazione dati`, `attacco hacker`; `filtración de datos`, `ciberataque`; `datalek`, `hack`; `violação de dados`, `ciberataque`; `vazamento de dados`, `ataque hacker`), the second about the fine, with the name of the authority where the press names it, and about the lawsuit (`Datenschutz Bußgeld`, `Klage`; `CNIL sanction`, `plainte`; `Garante privacy sanzione`, `causa`; `AEPD multa`, `demanda`; `Autoriteit Persoonsgegevens boete`, `rechtszaak`; `CNPD coima` and `ANPD multa`, `processo`). Each has at most three words after the name, because the Bing feed, on which the queries were tuned, lost recall on a longer query (see *Why these limits*), and the query normalizer leaves it as it is; a test holds the whole table to both, and to the rule that no two queries of a vendor are a repeat of each other.
- **Where they enter.** `suggestedQueries` gives them last, after the English queries and the query of the first other name, so the routine work (`planSearches`), the hints (a hint that repeats one is dropped) and the task of a run without the routine work all see them. The code makes them with the other news searches, paid for apart from the model's: four more searches for a vendor with a market, up to twenty in all inside the 30,000 ms of the routine work (the Bing feed, which was asked one search a second, is gone; GDELT is asked once for a run). The plan says the language of each, the briefing shows it (`- legal_regulatory: Brume Logiciels CNIL sanction (French) - 1 result`), and the [trace](#the-run-trace) records the query as for any search.
- **No `mkt`.** The engine is not asked for a market. Measured on the Bing news feed on 2026-10-28, before it was removed (not yet measured on the new engines), a query in the local language already returned local news on the default feed (German 8 results, French 2, Italian 9, Spanish 1, Dutch 11, Brazilian Portuguese 10), and `mkt=de-DE` and `mkt=es-ES` returned nothing for queries that return results without it.
- **The sources.** A source in the language of the market is a source like any other: the matcher, the lookback window, the source registry (the CNIL, the Garante, the AEPD and the data protection authorities of the Netherlands and Portugal are official sources) and the verification do not depend on the language. The analysis writes the findings in English and quotes a source in its own language, exactly as written; the loop prompt and the verifier prompt say the same. What the code does not do is tell that an English and a French article report one event (`clusters.ts` reads English words), so such a pair is left to the rule of the prompt that one event is one finding.

## The regulator in the query

The press that reports a fine or a settlement names the authority, and a query that names it finds those reports where `lawsuit` and `fined` find few (probed 2026-10-28 on the Bing news feed, since removed: `Adobe FTC` gave 8 items and `Adobe settlement` 7, `Blackbaud settlement` 11 with the multistate deal of the attorneys general among them, `Zoom FTC` 6, `Capita ICO fine` 11, `Meta DPC fine` 7, `Optus OAIC` 11, where `fined` alone gave none for Adobe or Blackbaud; a vendor with nothing on record gets none, which is no harm). So `suggestedQueries` adds two queries to the legal and regulatory news of a vendor that has no market of another language (`regulatorTopicsOf` in `market.ts`; a vendor with a market is searched with the authority of its country in its language, see above):

| Country domain of the website | Topic words | Query |
|-------------------------------|-------------|-------|
| `.uk` | `ICO fine`, `settlement` | `Acme ICO fine` |
| `.ie` | `DPC fine`, `settlement` | `Acme DPC fine` |
| `.au` | `OAIC`, `settlement` | `Acme OAIC` |
| any other, or no website | `FTC`, `settlement` | `Acme FTC` |

- **The country is read from the vendor's record and from nothing else**, as for the market: the country stated for the vendor (US, GB, IE or AU), else the domain. A stated US, GB, IE or AU decides whatever the domain and the legal form say, so `Acme GmbH` at `acme.de` stated as GB is searched in English with `ICO fine`. A domain such as `.com` says nothing of where a company is, and the American authorities (the FTC, the state attorneys general) are the ones that fine most companies that sell to American customers, so that is the default. The table is read by an own key, so a domain that is named like a property of an object finds no entry by accident.
- **They enter after the English queries**, before the query of the first other name and the queries in the language of a market, and like every other query they are made a short shape (the name and at most two topic words: on the Bing feed a longer query lost recall; `Okta fine regulator GDPR` gave one item). `site:` is not used anywhere: the Bing feed did not understand it.
- **What they cost.** Two more news searches for a vendor with no market, at one a second, so at most 18 searches (the 10 baseline, the 4 of other names and the 4 from hints) inside the 30,000 ms; a vendor with a market has at most 20.
- **What is not covered.** Canada has no entry: `Clearview Privacy Commissioner` gave 9 items and `Facebook Privacy Commissioner` none, so a query that names it is not reliable. A bare `SEC` drowns in stock news (`<name> SEC charges` is precise but finds little), and `attorney general` found next to nothing. The SEC's own filings are read directly (see below).

## Records of public databases

The news search finds what the press wrote. Public databases hold facts that the press often only repeats, and a database can be asked directly, with no model and no search: the vendor's name and domain are enough. A source of another kind is the vendor's own status page, which lists the outages that the press does not cover. So the code looks the vendor up in them before the first model turn (`gatherSources` in `gather.ts`), and what it finds enters the research as sources that were read: the databases as sources of `security_incidents`, the status page as sources of `availability` and the sanctions lists as sources of `legal_regulatory`.

Most of the lookup is the [vendor risk database](../domains/vendors.md#vendor-risk-database) (`vrdb/`): local copies of the CISA catalog of known exploited vulnerabilities, the sanctions lists of the United States Treasury (OFAC), the United Kingdom and the European Union, and the CVE Program's records, kept up to date by a scheduled job, and two databases that the run reads through, the National Vulnerability Database and the filings of the SEC, whose answers are stored for other runs. Beside it, a run still asks two sources itself (`records/`): Have I Been Pwned, and the incident history on the status page of the vendor. There is one switch for all of it, `VENDOR_RESEARCH_RECORDS`.

| Source | What it holds | How a run gets it | Records |
|--------|---------------|-------------------|---------|
| The CISA catalog of known exploited vulnerabilities, `www.cisa.gov` | The vulnerabilities that CISA has evidence of being exploited in the wild: the CVE, the vendor or project and the product, the name, the day it was added, the description, the required action, the due date and whether it is known to be used in ransomware campaigns | A copy, brought up to date every hour | At most 5, the newest |
| The National Vulnerability Database, `services.nvd.nist.gov`, no key | The critical vulnerabilities (CVSS base score 9.0 or more) published in the last 119 days (the API refuses a window longer than 120) for the products of one CPE vendor | Read through: asked at run time with `virtualMatchString=cpe:2.3:a:<vendor>`, where the vendor is the brand of the vendor's domain, else its name as one word, the severity `CRITICAL` and the dates of the window, and kept for 6 hours | At most 3, the highest score first |
| The CVE Program's records, `api.github.com` and `github.com` | The records that changed on a day, of which the critical (CVSS 9.0 or more) ones published in the last 24 months and every rejected one are kept | A copy, read by its daily changes from a baseline that an operator loads once | At most 3 |
| The filings of the SEC, `www.sec.gov` and `data.sec.gov`, no key | The Form 8-K filings that report Item 1.05, a material cybersecurity incident: since December 2023 a company registered with the SEC that has a material incident has to tell its investors within four business days, so this is the vendor's own report of an incident in its own systems, filed with a regulator | Read through, by the CIK stored on the vendor, else by the registrant whose name is the vendor's; every request names the Technical Support address of VerifyWise in its User-Agent, as the SEC asks, and kept for an hour | At most 3, the newest |
| The sanctions lists of the Treasury (`ofac`), the United Kingdom (`uk_sanctions`) and the European Union (`eu_fsf`) | The entities (companies and organizations) that a government has sanctioned, with the programs, the other names and the identifiers of each; a UK or EU entry shows the UN reference number when the United Nations made the designation | A copy, brought up to date four times a day | At most 2 of each list |
| Have I Been Pwned (`hibp.ts`, `haveibeenpwned.com`, no key) | The breaches of a service on the vendor's domain: the service, the dates, how many accounts, which kinds of data were exposed, whether the breach is verified, a description. A collection that is not a breach of the service (a spam list, a malware or stealer log, a fabricated or a retired entry) is left out | Asked at run time with the vendor's domain | At most 3, the newest |
| The status page of the vendor (`statuspage.ts`, fetched by `feedFetch.ts`, no key) | The incident history that the vendor publishes: the Atom feed `/history.atom` that a status page offers as its subscription feed (Atlassian Statuspage gives its latest 25 entries, incident.io about 100). Each entry is an incident or a planned maintenance, with its title, its day and its updates in the vendor's own words (`Investigating`, `Identified`, `Monitoring`, `Resolved`) | Nothing about the vendor leaves the server but the address: the feed is asked for at `status.<domain>`, `<brand>.statuspage.io` and `<brand without hyphens>status.com`, three guesses made from the domain of the vendor (a vendor with no domain has none) | A summary and at most 3 incidents, the newest |

- **The match is exact.** A database names a vendor with one string (the `vendorProject` of an entry, the vendor part of a CPE name, the domain of the service), and a record is the vendor's only when that string is a name of the vendor, letter for letter: its name and its other names, each as written and without the legal form, and the brand of its domain, compared as letters and digits only (`D-Link` and `dlink` are one; a name of fewer than two characters is not used). A label that merely contains the name or begins with it is not a match: `Apache` is a project of the Apache Software Foundation and not of a staffing company with the word in its name. The NVD matches the CPE vendor itself, whole, so a vendor whose name is not the one the NVD uses finds nothing, which is no harm. Have I Been Pwned matches the domain, case aside. A sanctions list is matched by the names of the vendor alone, never by the brand of its domain, and a name of fewer than four letters and digits is not looked up (`ABC` would find any company called ABC), so a name-only match is weak and the record says so. The SEC is matched by the stored CIK (strong) or by the names alone (weak: when registrants of different CIKs have the name it is not known which is meant, and the vendor gets no filing). The identifiers of the vendor (its LEI, registration number and CIK, and the verified domain of its website) are matched strongly where a list carries them; the keys and the rules are in [Vendors](../domains/vendors.md#vendor-risk-database). The status page is found by its address and not by a name: `status.<domain>` is the vendor's own, and a feed found at `<brand>.statuspage.io` or `<brand>status.com`, where any company may host a status page, is the vendor's only when its title holds a name of the vendor of three characters or more (`statusFeedNamesVendor`).
- **A record is a page that was read.** `session.addRecords` puts each record in the ledger (`kind: "page"`, not the vendor's own site, dated with the day it was published or added) with the record as its text, at a public address that shows it: the page of the CVE on `nvd.nist.gov` for the catalog and the NVD and on `www.cve.org` for the CVE Program, the breach in the API of Have I Been Pwned, the main document of the filing in the archive of the SEC (`https://www.sec.gov/Archives/edgar/data/<CIK>/<accession>/<document>`), for the status page the page of the incident (`https://<host>/incidents/<id>`) and the page that shows the history (`https://<host>/history`), and, for a sanctions list, the entry or the list's page with the entry's identifier. The entry also keeps the database that gave the record (`record`: `kev`, `nvd`, `cve`, `hibp`, `sec`, `statuspage`, `ofac`, `uk_sanctions` or `eu_fsf`), so that the [credibility label](../domains/vendors.md#credibility) classifies a record by its database and not by the host of its address, and, for a record of the vendor risk database, its id in the list, the strength of its match, the day of the copy and whether the copy is stale. A read of that address is refused as `already_read`, so the model has no reason to spend a read on it, and nothing is paid for the record: no search, no read, no call of the category. The lookback of the category of the record applies (a record older than the window is left out and counted; 12 months for the status page, 24 for the databases; a designation on a sanctions list is a state, so it is exempt), an address that the ledger already has is left out, and the records go in before the searches are made, so they come first among the sources of the category and the pack gives them up last. Because the source is a page and not a search result, a finding that cites only records is not marked `snippet_only`. A CVE that the catalog lists and the NVD scores is one source at the address of the CVE, with the words of both, and a CVE that one list offered is not offered again by a later one.
- **The text is the database's.** A record is plain text that starts with the name of its database (`CISA Known Exploited Vulnerabilities Catalog (cisa.gov).`, `National Vulnerability Database (nvd.nist.gov).`, `CVE Program (cve.org).`, `Have I Been Pwned (haveibeenpwned.com), licensed under CC BY 4.0.`, `SEC EDGAR (sec.gov).`, or the name of the sanctions list) and goes on with its fields as sentences, so a quote is the database's own words. A record of a status page starts with `Status page of <name> (<host>).` and goes on with `Incident:`, `Date:` and `Updates:` (the updates of the incident, newest first, each with its time and its label); its summary holds the number of entries of the feed and the days they cover, the number of incidents since the cutoff of the category, the number of planned maintenances, and, when the feed does not reach back to the start of the window, the sentence that earlier incidents are not counted. A record of the SEC holds `Company`, `Form`, `Filed`, `Items reported` and, when the filing could be read, `Item 1.05:` and the text of the item, up to 2,500 characters: the vendor's own description of the incident. A record of a sanctions list holds the entry, the programs, the other names (6 at most, and how many more there are), the remarks (600 characters at most, cut at a `;` or a space with a marker when longer), the identifiers, the UN reference number where the entry has one, a note of the lookup when the vendor was matched to the entry by name only ("an entity named … is on …": the entry may be another company with the same name), and the day of the copy ("As of …"). The catalog, the NVD, the sanctions lists of the Treasury and the SEC are works of governments and free to use, the UK list is under the Open Government Licence v3.0, the EU list under the Commission's reuse notice, the CVE Program under its Terms of Use (MITRE's copyright designation and the licence are stored with the copy and shown in the coverage), and the data of Have I Been Pwned is licensed under Creative Commons Attribution 4.0, which is why each of its records names it as the source.
- **Credibility and prompts.** A record is classified by its database, and not by tiers of hosts (`classifyRecord` in `sourceRegistry/classify.ts`; the confidence ceiling and `sourceTiers.ts` are gone): the catalog and the NVD are official with a strong match, the SEC and the sanctions lists official with a weak one when found by name, Have I Been Pwned unverified, and the status page the vendor's own word. The briefing marks the sources that are records with `(record)` and tells the loop that they are already in its evidence; the analysis prompt tells the model that a record of a vulnerability is about a flaw in a product and not about a breach of the vendor's own systems, that it should write which it is, and that the catalog lists only vulnerabilities that are exploited in the wild while the NVD and the CVE Program list flaws, most of which are not; a record of the SEC is a Form 8-K that the vendor itself filed under Item 1.05 to report a material cybersecurity incident, its own statement to its investors. The prompt tells the model that a source whose text begins with the name of a sanctions list and "An entity named … is on …" is an entry that has the name of the vendor and that the name is all the match is, that it shows that a company of that name is sanctioned and never that the vendor is, that it should raise at most one risk from it, in `legal_regulatory`, rate its likelihood `Possible` at most and make the action plan a check of who the vendor is against the entry; an entry without that note matched the vendor's verified website or one of its identifiers, and is about the vendor unless the identifiers it lists say otherwise. A source whose text begins with `Status page` is the incident history that the vendor published, a minor incident alone is not a risk, and the page lists only its latest incidents. The verifier is told which public database a cited record is an entry of (the `database` attribute of the source in its prompt, `vr-12`), since one quote cannot hold both the name of the database and the description: an entry of the CISA catalog says that the flaw is exploited in the wild, while an entry of the NVD or of the CVE Program says only that it was published. Each record is about one category, so a loop is told only of the records of its own: the loop for `security_incidents` of the databases, the loop for `availability` of the status page, the loop for `legal_regulatory` of the sanctions lists.
- **Who filed an EDGAR filing (Q28).** EDGAR shows a filing under the folder of every party to it: a Schedule 13G that an investor files about the vendor, or a Form 4 that an insider files, sits beside the vendor's own 10-K. So a cited filing under the CIK stored on the vendor is the vendor's own word only when the filing's SGML header (`<accession>.hdr.sgml`, on `www.sec.gov`) names that CIK as a filer, a person the filing is filed by or a reporting owner. `edgarFiler.ts` reads the header: `accessionOfFiling` takes the accession from the archive path or from the viewer forms, `parseFilingRoles` scans the header line by line (at most 256 KB, anchored per-line patterns, keeping roles and CIK digits only and never a name or an address, and reading both the tag layout and the text layout of a header), and `filerRoleOf` answers `vendor` (the stored CIK holds a filing role), `other` (it appears only as the subject company or the issuer, or not at all) or `null` (the turn was refused, the fetch failed or the body was cut). It runs in the analysis, before the labels, for the sources that the kept findings cite, at most 5 headers a run and 30,000 ms for all of them, each on a turn of the shared SEC spacer with the SEC User-Agent, and answers are remembered for a day per accession. A filing with `other` or no answer is `unverified` and downgraded, as every filing a third party can file under a company's folder was before (Q26). The trace logs counts only, and the log lines are fixed words by kind.
- **Manners and limits.** The lookups of the categories that the run researches are made together, in 8,000 ms for all of them (the status page is asked only when `availability` is researched and the databases of security incidents only when `security_incidents` is); a database that has not answered by then has failed. The answers of Have I Been Pwned are kept in the memory of the process for 6 hours (200 vendors), the status page feeds for an hour (200 hosts), and runs that ask while a load is going on share it. A database that fails is left alone for 5 minutes: the lookups in that time answer `failed` at once, with no request, so a blocked host costs one wait and not one for every run, and a run that was cancelled does not start the rest. A failure is an answer and not an error, in the words of a read that failed; only a bug is thrown. The NVD allows 5 requests in 30 seconds without a key, for each client: the workers of the application make at most 4 together (`spacer.ts`, a rolling window that `sharedSpacer.ts` keeps in Redis under `vrdb:spacer:nvd`, where one script reads the clock of Redis, drops the starts that left the window and takes a turn at once, so two workers never take one place), and a request that would have to wait more than 3 seconds is not made, so the NVD is reported unreachable for that run; it is not left alone for that, because it was busy and not down. A turn is refused the same way when Redis does not answer within that time, fails, or is reconnecting. The SEC asks automated clients to name themselves and allows at most 10 requests a second; the SEC spacer (`vrdb:spacer:sec`) takes 5 a second, waiting 2 seconds at most. The databases are published APIs and files, so, like the search, they are requested through the guarded fetch (the address policy, the size limit and the User-Agent apply) without a `robots.txt` check, but for the status page, which asks. The text of a filing is a page and not a data file, so it is read through the run's page reader with the SEC User-Agent (`robots.txt`, the guard and the cache of the run apply; the archive is open to robots): a filing that cannot be read, or whose text holds no Item 1.05, is a record of its facts alone, which is no failure of the lookup.
- **The status page.** A status page offers the history of its incidents in three ways, and one is used. The JSON API of Atlassian Statuspage (`/api/v2/incidents.json`) is not: the `robots.txt` of the status pages that were probed on 2026-10-28 (`www.githubstatus.com`, `status.datadoghq.com`, `status.atlassian.com`) disallows `/api/` and `/embed/` for every robot, and the research does not read what a site asks robots to leave. The page `/history` is built by a script and holds no text of the incidents. The Atom feed `/history.atom` is what the page itself offers as its subscription feed, and the same `robots.txt` allows it, so it is the source; Statuspage and incident.io both serve Atom. `feedFetch.ts` fetches it through the guarded fetch with the robots check of the page reader (the `robots.txt` of the origin is asked for the first address and for every hop of a redirect; one that cannot be reached disallows everything, one that is missing or refused disallows nothing). An answer that is not an Atom feed (an RSS feed, a page of HTML, a feed larger than 2 MiB) is no status page. The feed is read by a scanner written for it, with no XML library and aware of CDATA. The root must be `<feed`, after white space and any number of processing instructions (the XML declaration, a style sheet) and comments. An entry has the day of its `published` time, else of its `updated` time (an RFC 3339 time, taken in UTC; a time with no zone, an offset with no colon, or words around the date make it no date, and an entry with no date is left out), the id of the incident from the path `/incidents/<id>` of its alternate link (letters and digits, 40 at most; a link with no address is passed over), a title, and its updates as plain text: the content, else the summary when the content has no words, turned into text by `htmlToText` of the page reader. The limits are 200 entries, 1,500 characters of text, 200 of title and 100 of the name of the page, each cut without a space left at its end. The feed is served by a host that the vendor does not always control, so reading it takes time in proportion to its size whatever it holds: the root is read by hand and not with a pattern (comments in a row made a pattern that takes exponential time to fail), a tag of a link reaches to the next `<` at most, the white space around the label of an update is bounded, and the text of the updates is the page reader's, which was built for hostile pages. The tests feed the parser such feeds and require two seconds at most. An entry is a planned maintenance when its updates are labelled `Scheduled`, `In progress`, `Verifying` or `Completed` and none is labelled `Investigating`, `Identified`, `Monitoring`, `Resolved` or `Postmortem`: a maintenance is counted in the summary and is never a record. An entry dated after the day of the run is not read. The three guesses are asked together, and a host that is not there, that does not answer, that `robots.txt` closes to the bot or that serves something else is no status page and no failure: a vendor with no status page gets no records, the lookup is `empty` and never `failed`, and the status page is never left alone for five minutes. A feed that was found, and an answer that was not a feed (`not_found`, `unsupported_type`), are kept in the memory of the process for an hour (200 hosts); an answer that failed because the site did not answer in time is forgotten at once.
- **The sanctions lists.** The Treasury's Sanctions List Service serves the two files of the SDN list at `sanctionslistservice.ofac.treas.gov/api/PublicationPreview/exports/SDN.CSV` and `.../ALT.CSV`, each by a redirect to a store (an Amazon S3 host of the GovCloud region, today `wc2h-sls-prod-public-published.s3.us-gov-west-1.amazonaws.com`, so the egress of the server has to be open to it too); the `robots.txt` of the service is a 404, and the files are the documented way to get the list. The scheduled job reads them (`vrdb/connectors/ofac.ts`) with a CSV reader written for them (`parseCsv`): a field in quotes may hold commas, line breaks and quotes written twice, lines end with LF, CRLF or CR, a quote that is never closed ends at the end of the text, and the text is read once from the front, so the time is that of its length whatever it holds. The files have no header row: an entry has 12 columns and a field with nothing in it is written `-0- `; an entity is an entry whose type is empty, and the types `individual`, `vessel` and `aircraft` are left out. The other names are read for the entities only, 250 at most for one entity, and a remark longer than 600 characters is cut at the last `;` or blank that leaves room for a ` [shortened]` marker. The UK list is one XML file from `sanctionslist.fcdo.gov.uk` (entities only; the host of each website is a domain key, and an e-mail address typed into the field is none) and the EU list one XML 1.1 file on `webgate.ec.europa.eu` that the operator's RSS feed names (enterprises only; the host of each website in the contact details is a domain key); both show the UN reference number of an entry the United Nations designated, in its text and its identifiers, never as a key.
- **What can be seen.** Each lookup is a step of the [trace](#the-run-trace) (`tool: "gather"`, `by: "code"`, the category, the address that was asked, the outcome `ok`, `empty` or `failed` with its reason, the number of records, what was left out as `old` or `more`, and the milliseconds). The briefing lists the databases with the number of records each gave (the loop for `availability` is told of the status page, the loop for `legal_regulatory` of the sanctions lists, the loop for `security_incidents` of the others), and says so when one could not be reached. The lookup of the status page names the address of the first feed it guessed, and the address of the feed that was found once there is one. The coverage of the run (which list was checked, its outcome, its mode and the day of its copy) is stored on the run and shown under it.
- **The vendor risk database is always on.** It has no flag of its own: `gatherSources` asks the lookup of the vendor risk database (`vrdb/lookup.ts`), which reads the local copies of the catalog and of the OFAC, UK and EU sanctions lists, the CVE Program's records, and the stored answers of the NVD and the SEC, beside the two web lookups of Have I Been Pwned and the status page (`sourcesBesideVrdb`). The run's own lookups of the catalog, the NVD, the SEC and the OFAC list were removed when the database became the only path. A record of a copy enters the ledger as a record of the web does, before the searches: its text is the list's own, ends with the day of the copy ("As of …") and, for a match by name alone, holds the lookup note, and its entry keeps the row of the record, its id in the list, the strength of its match, the day of the copy and whether the copy is stale, which the [credibility label](../domains/vendors.md#credibility) reads (`provenanceOf`).
- **The read-through.** The vendor risk database asks the NVD and the SEC itself, at run time (`vrdb/readThrough.ts`, `connectors/nvd.ts`, `connectors/sec.ts`). The NVD request is by the vendor's CPE vendor token (the critical CVEs of the last 119 days) without the run's cutoff, so that one answer serves every run of every organization for 6 hours, and the lookback applies when its records are offered. The SEC is asked by the stored CIK, else by the registrant whose name is the vendor's, and an answer is kept for an hour. A request takes a turn of the shared spacer above, within the run's 8 seconds; the answer is stored in the tables of the copies, and a failure offers the stored records and leaves the key alone for 5 minutes.
- **The sources behind a gate.** Two sources are open since 2026-10-31 and one is closed (`vrdb/gates.ts`, see [Vendor risk database](../domains/vendors.md#vendor-risk-database)). The SEC (Q4) is read through with the User-Agent `VerifyWise tech@verifywise.ai`, the Technical Support address of verifywise.ai/contact, as the SEC asks of automated access, on a turn of a second shared spacer (`vrdb:spacer:sec`, 5 requests a second, half of what the SEC allows, a wait of 2 seconds at most). The CVE records (Q7) are read by their changes: the GitHub API answers the release of a day by its tag (`api.github.com`), and its asset, the zip of that day's changed records, is downloaded from `github.com`, which redirects to `release-assets.githubusercontent.com`; a day before yesterday that has no end-of-day release is read from its last hourly release, which the GitHub API lists by the day's tags (`git/matching-refs/tags/cve_<day>_`); the zip is read by a reader of the job's own (`vrdb/zip.ts`: the central directory, Zip64, stored or deflated entries with their sizes and CRC-32 checked, a zip inside the zip once), within fixed limits of entries and bytes. The CVE records need a baseline that an operator loads once with `scripts/vrdbCveBaseline.ts` (see [Vendors](../domains/vendors.md#vendor-risk-database)); nothing downloads it, and the scheduler queues no first sync for this list. The UN list (Q6) is one XML file at `scsanctions.un.org`, which redirects to a time-limited address on `unsolprodfiles.blob.core.windows.net`, read with a conditional GET by the scanner below; its gate stays closed, since the UN's terms of use allow personal, non-commercial use only, and opens only with the UN's written permission, so no run contacts those hosts. The designations of the UN reach a run through the UK and EU lists.
- **The copies.** A scheduled job brings each copy up to date (see [Vendor risk database](../domains/vendors.md#vendor-risk-database)). It downloads a list through the page guard with a conditional GET (`guardedConditionalFetch` in `guardedFetch.ts`, with every check of `guardedFetch`): the ETag and the Last-Modified of the last download go out as `If-None-Match` and `If-Modified-Since`, each only when it is a value a header may hold, and a 304 on the last hop, after redirects too, says the copy is current; a 200 answer carries its own validators for the next download. The UK and EU lists are XML files (a download is cut at 64 MiB, the catalog at 8 MiB, the two OFAC files at 16 and 8 MiB), read by a scanner of the job's own (`vrdb/xmlScan.ts`, no dependency): one pass from one `<` to the next with `indexOf` and `charCodeAt` and no regular expression, so a file of any size or shape is read in time in proportion to its size; it keeps only the elements of the one name it is asked for, drops namespace prefixes, skips comments and processing instructions, reads CDATA as text, decodes the five entities and numeric references once, and refuses a DOCTYPE with an internal subset, so an entity that a document declares is never expanded. A malformed tag or an element left open is counted as an error, and a sync with errors leaves the copy as it was.
- **The off switch.** `VENDOR_RESEARCH_RECORDS=false` turns the whole lookup off: the scheduled copies stop, the read-through is not asked, and Have I Been Pwned and the status page are not looked up, for a host that cannot reach these sites or a policy that says no (see [Configuration](../domains/vendors.md#configuration)). The worker and the backend read it. With it off every list is reported as `off` in the coverage of the run, and the screen says "Public databases turned off".

## The pages where the vendor states its terms

A vendor's terms, privacy policy, data processing addendum, list of subprocessors and security page change without a press release, and the memory of the sources would not show a scheduled run a page it has seen. So the research watches these pages on its own (`policySnapshots.ts`; the rules, the table and the limits are in [Vendors](../domains/vendors.md#policy-page-changes)):

- **Noting.** `collectPolicyPages` wraps the page reader that the researcher gives the web session, so the model's reads and the routine work's reads pass through it. A page of the vendor's own site (decided on the address that answered, like the session's own mark) whose address or title says it states the vendor's terms is noted with its whole text, which the ledger's excerpt does not hold. The check of the website and the sitemap read around the session, and the reader that the analysis uses is the reader itself, so none of them notes a page. The result of the researcher carries the pages as `policyPages`; a researcher that does not give them leaves the pages unwatched.
- **Comparing.** The pipeline (and only the pipeline: the toolkit knows nothing of it) reads the text kept for the vendor, compares line by line as sets, and turns each page that really changed into a ledger entry that comes first in its category. A first visit, an unchanged page and a change of fewer than 40 characters make no entry.
- **Writing.** The text of the pages is written after the run is saved, for a run that completed only.
- **No new request.** It reads no page that the run did not read, so the pages the guard allowed are the pages that are kept, and nothing new leaves the server (see [What leaves the server](#what-leaves-the-server)).

## The shared cache

Runs share four caches in Redis (`webCache.ts`; `vendorResearch/researchCache.ts` connects them to the application's Redis client), so that a second run of a vendor, or two vendors on one platform, do not ask the web for what a run asked a moment ago.

| What | Key | Kept for | Largest entry |
|------|-----|----------|---------------|
| The `robots.txt` of an origin | The origin | 24 hours (RFC 9309, 2.4 allows no more) | 64 KiB |
| A page that was read | The address as the URL parser writes it, without the fragment | 15 minutes | 512 KiB |
| The answer of a search of a provider (Claude's search) | The engine, the organization, the kind and the words of the query, in lower case with the spaces squeezed | 10 minutes | 64 KiB |
| The index of a GDELT request | The address of the request | 1 hour | 256 KiB |

- **A hit costs nothing.** No request, no wait in the search queue (the 5 seconds between requests to GDELT) and no draw on a site's patience. It still counts as a search or a read of the run's budget, so that what a run does does not depend on what the cache holds.
- **Only what worked is kept.** A page that failed, a search that failed and a `robots.txt` that could not be fetched are asked again. So is a `robots.txt` that the site refused to show (401, 403, 429), since that can be the firewall of the moment; a text, and a file that is not there (404, 410), are kept. A search that found nothing is an answer and is kept. Within a run the session still does not try a failed page twice (`already_failed`).
- **Public content, shared by all organizations, with one exception.** A key of a page, a `robots.txt` or a GDELT index names no organization, an entry holds nothing about one, and the pages are fetched with no credentials and one bot identity, so two organizations get the same entry (the GDELT index is public data that the GDELT terms let anyone redistribute). The exception is the answer of a search of a provider: it was bought with one organization's key, so its key names the organization, and an answer is never served to another. The key also names the engine, so the answers of two engines never mix. The key in Redis is the SHA-256 of the logical key under `vr:web:v1:<kind>:`, so an address or a query never sits there as text. Raise the version in the namespace when the shape of a stored value changes.
- **The store is not trusted.** An entry is parsed and its shape is checked, and every address in it must be public again. An entry that fails is a miss, and the next write replaces it.
- **It can never fail or slow a run.** Every operation ends within 250 ms, a Redis that is not `ready` is not handed a command (the shared client has `maxRetriesPerRequest: null`, which would queue the command until the connection returns), a write is not waited for, and any failure is a miss. The client is loaded on the first lookup, so a process that never researches never needs it. Without Redis the research behaves as it did before the cache.
- **Where it applies.** `createVendorResearcher({ cache })` gives the cache to the reader and to the engines it builds (the provider's search through `withSearchCache`, GDELT for its own index and `robots.txt`), and the job passes `sharedWebCache()`. An engine or a reader that is injected is used as it is. The evaluation harness passes none: a live evaluation measures the web, not the cache.
- **Observed** by the counter `vendor_research.cache` (kind `robots`, `page`, `search` or `gdelt`; outcome `hit`, `miss` or `error`, a failed write included) and, when the store fails, by one warning a minute at most, which names no key.
- **Memory.** Entries are bounded in size and in time. The Redis is the one BullMQ uses, which asks for `maxmemory-policy noeviction`, so the cache is bounded by its lifetimes and its size limits and not by eviction; a run reads at most 12 pages, and a page is 10 to 50 KB of text as a rule.

## The run trace

A run keeps a **trace**: the record of what the agent did and what became of it, so that a person can tell why a run found what it found, and so that a change to the agent can be measured. It is stored on the run (`vendor_research_runs.trace`, JSONB, null for a run from before the column and for a run that failed before it started) and is built by a recorder (`trace.ts`) that the pipeline hands to the research, the model calls and the checks of the analysis.

| Part | What it holds |
|------|---------------|
| `steps` | The check of the website (`preflight`), the read of the sitemap and the lookup in each public database (`gather`: the address that was asked, the number of records and what was left out of them, never the text of a record) and the searches and reads that the code made before the loop (`by: "code"`, no `turn`), then every search, read and refusal in order (a search of a kind the engine does not answer is a refusal with the reason `kind_unavailable`), and last the pages read by the check after the analysis (`by: "verification"`, outcome `confirmed`, `not_on_page` or `failed` with the reason of the failed read; never the quote or the text of the page): the loop that took it when there is one for each category (`loop`, the category), the model turn that asked for it (`turn`, shared by the actions of one step, numbered from 1 in each loop), the tool, the category, the query or the address (and `part`, for the read of a part of a long page, which costs no page read), the thought of the model, the outcome (`ok`, `empty`, `refused` or `failed`), a reason from a closed set of words, how many results were kept, what was left out of them by reason, and the milliseconds |
| `modelCalls` | Every model call: what it was for (`loop`, `hints`, `analysis`, `verifier`, or `search` for a search of Claude's web search, billed to the key), the milliseconds, the attempts, the input, output and total tokens as the provider reported them, and whether it ended by throwing |
| `rejected` | The candidates (and quotes) that validation, de-duplication or the caps turned away, with the stage, the reason, the category and the start of the text |
| `dropped` | Counts by `kind.reason`: `citation.` (a quote the validation removed), `duplicate.` (a candidate the de-duplication dropped: `active_risk`, `earlier_finding`, `same_source`, `same_run`, or `same_event` when the sources it cites report an event that a kept candidate cites), `cap` (a candidate over the limit of 3 per category and 8 per run), `verifier.` (a finding the verifier took away: `other_company`, `not_supported` or `out_of_window`) and `source.` (a result or page left out before the evidence, by reason: `old`, `off_topic`, `duplicate`, `bad_address`, `same_text`; the step carries the same counts as `omitted`; and `already_seen`, a source that a scheduled run set apart because an earlier run showed it to the model, which is counted for the run and is on no step) and `page.` (a page where the vendor states its terms that made no source of change: `first_visit`, `unchanged` or `minor`; counted for the run, on no step) |
| `phases` | The milliseconds of each phase (`research`, `analysis`, `validation`, and `verification` when the findings were checked against pages) |
| `totals` | Model calls and tokens, added up |
| `stoppedBecause` | Why the loop ended: `finished`, `budget`, `steps`, `time` or `model_error` |

Everything is bounded so that storing the trace cannot fail a run: at most 150 steps, 80 model calls and 100 rejections, every text cut to a character limit, and a snapshot of at most 200,000 bytes (`truncated` says when a list reached its limit). Text that a third party or the model wrote (a query, an address, a thought) is cleaned like the evidence is, because Postgres refuses a NUL and a lone surrogate in JSONB.

The tokens come from the AI SDK's `usage` of each call. `generateObjectWithSelfCorrection` reports them through `onUsage` once per model call, including a failed attempt that reports its usage (the SDK's `NoObjectGeneratedError` carries its own), so the trace shows what a run cost even when the answer had to be asked for again or the call ended by throwing.

The trace is not the **live progress** of a run. While a run works, the pipeline hands the researcher a `progress` callback (`ResearchProgress`: the turns taken, the latest action and category, the searches and pages so far and the categories worked on), which the observer of the loop calls after every turn, and writes what it gets to `vendor_research_runs.progress` for the page that follows the run. It holds counts and closed words only (no query, address or thought, which is why every role may read it), it is emptied when the run ends, and a callback that throws changes nothing in the research. See [Vendors](../domains/vendors.md#live-progress).

The trace holds queries and addresses, which the run summary that every role sees does not, so it is served to administrators only: `GET /api/v1/vendors/:id/research/runs/:runId/trace`, gated by `llmKeys.admin` (the built-in Admin role). It answers 404 for a run without a trace and for a run of another organization. See [Vendors](../domains/vendors.md#vendor-research-endpoints).

## Evaluating the agent

A change to the agent is judged on cases, not on one vendor that happened to be on the screen. `Servers/services/vendorResearch/eval/` holds a set of **cases** and a harness that runs the agent over them.

A case (`types.ts`) is a vendor, a **recording** of everything a run needs from outside (the steps the model took in the loop, what each search and each page read answered, and the analysis the model gave), what a person would have wanted from the run (the findings it should keep, and the events it should report only once) and the **targets** that say whether the agent gets there. `runCase.ts` replays the recording through the **real** researcher (the loop, the web session, the guarded rules) and the **real** `analyse` (validation, de-duplication, caps), with a replay search engine, a replay page reader and a scripted model (`replay.ts`). Nothing touches the network, a database or a model, so a case runs in a unit test and gives the same answer every time. The tokens of a replay are estimated (characters over four), the ones of a live run are the provider's.

`scorer.ts` measures a run on what a person would check by hand:

| Measure | What it counts |
|---------|----------------|
| `precision`, `recall` | Kept findings that match an expected finding (category and words), and expected findings that a kept finding matches |
| `citationsRejected`, `candidatesRejected` | Quotes and candidates that validation removed |
| `irrelevantSources` | Sources of the pack that do not mention the vendor |
| `duplicateSources` | Sources whose text is the text of an earlier one |
| `badUrls` | Addresses that end in an encoded quotation mark |
| `datedWebResults` | Results of a web search that carry a date (an engine that gives one gives the day it saw the page, see [The search engine](#the-search-engine)) |
| `snippetOnlyFindings` | Findings that cite snippets only: no cited source is a page that was read, and no page that the run read, after the analysis too, holds a quote they cite (looked up in the text the reader gave, not taken from the mark on the finding) |
| `mislabelled` | Findings whose [credibility label](../domains/vendors.md#credibility), or name-only note, is not the one that the case gives the expected finding they match (`credibility` and `nameOnly`; the first expected finding that matches and gives a label). The label is computed by the code it checks, so it is held to what a person wrote |
| `duplicateClusters` | Findings beyond the first about one event |
| `searches`, `reads`, `modelCalls`, `ms`, `tokens` | What the run cost |

The cases are the failures of the real runs, each written to reproduce one (`cases/`): a breach that two publishers report, a vendor the search engine does not know, one story on two domains of one publisher, one article under two addresses, an address that ends in a quotation mark, one attack reported as three findings, an old story with the date of its crawl, a finding that rests on a snippet whose page holds the quote, one whose page does not, findings that the verifier takes away (another company, an overstated claim, an old matter), a clause that sits in a later part of a long policy, and a vendor with a clean record. Eight more are worked cases of the credibility rule (spec D5.7 of `docs/superpowers/specs/2026-10-29-vendor-risk-database-design.md`): two trusted publishers, the copies of one agency story, a post of a user, a vendor's claim about itself, a vendor's notice of its own incident, the page of a regulator, two trusted publishers whose pages cannot be read, and a contributor's post on the site of a publisher. Nine more hold copies of the lists of the vendor risk database (`recording.vrdb`: the rows of the records, the state of each copy and, for a read-through source, what it answered for the run, `readThrough`: its key, whether that key is weak, and the outcome and day of the answer), which the runner offers through the lookup's own `offerRecords` with no database (`runCase.ts`; like the lookup's query, the runner leaves out a vulnerability whose CVE has a rejected row on any list): a CVE that the catalog withdrew, a sanctions entry that its list delisted, a copy that is three days out of date (`expected.coverage.stale`), one name on the OFAC and the UK lists, a UK entry whose website is a page on the social network that holds the vendor's own page (`platform-website`), which no run is offered, a KEV entry whose CVE the CVE Program rejected (`rejected-cve-mirror`), offered by no list, a UK entry with the vendor's name and registration number (`identifier-match`), High, a CVE that the NVD answered when it was asked at run time (`nvd-read-through`), High as of the day of the answer, and an EU entry that carries the vendor's LEI under a name the record does not hold (`lei-match-other-name`), High: the entry's text shows the LEI, and a citation of a record whose text carries the vendor's stored LEI counts as about the vendor (`validation.ts`). Every expected finding names the label it should get, and every case holds `maxMislabelled: 0`. There is one set of rules, so nothing is replayed twice; the label never reads a confidence of the model, which the analysis no longer asks for.

**The ratchet.** A case lists in `targets` what the agent should reach and in `gaps` the roadmap idea (`docs/superpowers/plans/2026-10-27-vendor-research-agent-performance.md`) that is meant to make it reach a target it does not reach yet. The test of the cases (`__tests__/cases.test.ts`) fails when a target is missed and is not a declared gap (a regression), and when a declared gap is met (it was fixed: delete its line). So fixing something means deleting its gap, and breaking something cannot pass.

**The command line.** From `Servers`:

```bash
npm run eval:vendor-research                           # every case, replayed
npm run eval:vendor-research -- --cases breach-two-publishers,clean-record
npm run eval:vendor-research -- --json                 # the reports as JSON
npm run eval:vendor-research -- --live --org <organizationId> --vendor "Acme" --website acme.com --provides "Payroll software"
npm run eval:vendor-research -- --live ... --record acme.json   # also write the recording of the live run
npm run eval:vendor-research -- --live ... --trace acme-trace.json # also write the trace of the live run
```

It exits 0 when there is no regression and no fixed gap, 1 when there is one, and 2 for a bad argument. `--live` runs the real agent for one vendor with the organization's own LLM key and the real web (the key is read from the database and never printed); `--record` captures that run as a recording, which a person can then turn into a case. A replay tests only what the code does with a given model answer, because the scripted model does not react to a prompt: whether a better prompt makes the model search better can only be seen live.

## Adding another engine

An engine is one more implementation of the `SearchEngine` interface, and nothing else changes: the loop, the session and the guard see only the interface. Which engine a run gets is decided in one place, `createRunSearch` in `researchAgent.ts`, from the `search` spec that `searchEngineOf` (`vendorResearch/searchEngineOf.ts`) derives from the research key: Claude's search for an Anthropic key, GDELT for every other.

1. Write an object with `id`, `kinds` (the kinds of search it answers), `newsWindowMonths` (how far back its news reaches, or `null`) and `search(query, kind, signal)`. Add its id to `SearchEngineId` and to the CHECK constraint of `vendor_research_runs.search_engine` (a migration), so that the run can record it. `search` resolves with at most 10 `SearchResult`s (`title`, `url`, `snippet` of at most 1,500 characters, `publishedAt` as an ISO date or `null`, `source` or `null`), and with an empty list when there is no result. For any failure, an abort included, it rejects with a `SearchEngineError`; any other error the session treats as a bug and passes on.
2. Make its requests through `guardedFetch`, so that the URL policy, the address policy and the limits apply to it as well, and ask the `robots.txt` of its host. If the service limits the rate, reuse `createSearchQueue` with the gap it asks for, and share the queue of the process (GDELT counts requests by address, and a worker runs several researches at once).
3. Return result addresses that a page can be read from: not a redirect or tracking wrapper of the engine itself. The session still checks every address with `parsePublicUrl` and drops one that fails.
4. Decide what happens when the engine cannot answer: a provider engine that is refused (400 or 404) throws `SearchUnavailableError`, and `withFallback` moves the run to the engine that always works (GDELT). Put the answer cache around the first engine only (`withSearchCache`, scoped to the organization for a provider that bills the key), so that an answer of the fallback is never filed under the key of the first.
5. Check the terms before anything else. The engine of this page was chosen because its terms allow storage, display and commercial use (brief 2.3 (d) of the vendor risk database design), and the Bing feed was removed because its terms did not. If the engine needs a key or an account, keep it in the environment only, never read it into a log line or an error message, and note that this changes the product promise that research needs no account beyond the LLM key, so it is a decision for the product owner.

## Cost and how long a run takes a worker

A typical run is 8 to 16 steps. Each step sends the prompt, the history and the budget, about 6,000 to 8,000 input tokens, so the loop reads roughly 60,000 to 130,000 input tokens, and the analysis another 20,000 to 30,000. On a DeepSeek-class price that is cents; on a frontier-model price it can be a dollar or more. These are estimates. The organization pays on its own key. The daily cap (default 50 runs per organization) bounds the cost, and `VENDOR_RESEARCH_AUTO_RUN=false` removes the automatic part. A run records `searches_used` and `pages_read` for the tool side; the provider's usage page measures the model side. The search has a price of its own on an Anthropic key: about $10 per 1,000 searches, billed by Anthropic to the key, and a run makes about 20 to 30 searches (10 to 20 of the routine work, up to 8 by the model, 4 by hints), so about $0.20 to $0.30 in fees, plus the tokens of each search call, which can cost more than the fee. The daily cap bounds it. A key that is not Anthropic's searches the news of the last 3 months through GDELT for nothing (the research settings tell an Admin both).

A run can occupy a place of the research worker for about 7 minutes (up to 5 for the loop, 2 for the analysis and half a minute for the checks after it) and is cut off at 20 minutes (`RUN_TIME_LIMIT_MINUTES`: the pipeline fails it as `timed out`; the sweep of the stuck runs waits 25 for a running run). Research has a queue and a worker of its own, which take five runs at a time for each worker process (`VENDOR_RESEARCH_WORKER_CONCURRENCY`) and nothing else, so a burst of runs no longer holds up the other background jobs. It can still leave the last of many runs queued past the 15-minute limit of a queued run, which ends it as `timed out`; the answer is **Research again**, a higher setting or another worker process.

The hourly job of the [scheduled scan](../domains/vendors.md#the-scheduled-scan) is on the same queue and holds a place for moments, since it only starts runs. The runs it starts cost what any run costs, are held to the daily cap, and are limited to half of it and to 5 vendors an hour for each organization. A scheduled run analyses only the sources that earlier runs did not show to the model, so its analysis call is smaller than that of a first run, and absent when nothing is new; the loop that finds the sources is the same.

## Testing without the network

No unit test touches the network or a real model. Everything that would is injected:

| What | How |
|------|-----|
| The HTTP request | `guardedFetch(url, options, { transport, dnsLookup })`: a fake transport answers from memory, a fake lookup returns the addresses the test wants |
| The fetch of a reader or an engine | `createPageReader({ fetch })` and `createGdeltEngine({ fetch, queue, robots, now, sleep })` take a fake `guardedFetch`, a queue with no wait, a `robots.txt` checker and a clock; `createProviderSearchEngine({ model, generate })` takes a scripted `generate` |
| The headless browser | `createChromiumRenderer({ launch, fetch })` takes a scripted stand-in for the browser (`__tests__/renderPage.test.ts`), `createPageReader({ render })` and `createVendorResearcher({ render })` take a fake renderer |
| The shared cache | `createPageReader({ fetch, cache })`, `createGdeltEngine({ fetch, queue, cache })`, `withSearchCache(engine, cache, scope)` and `createVendorResearcher({ cache })` take a cache; the unit tests give them `memoryCache()` (`__tests__/helpers/memoryCache.ts`), and `tests/integration/vendorResearch.webCache.test.ts` runs the Redis adapter on a real Redis |
| The page and the search of a session | `createWebSession({ engine, readPage, ... })` takes a fake engine and a fake `PageReader` |
| The model | `runResearchLoop` and `createVendorResearcher` take a scripted `generate`, a function that returns the steps the test wants |
| The whole research of a run | `PipelineDeps.research` takes a fake `VendorResearcher`, so pipeline tests need neither a model nor the web |
| A whole run, end to end | `runEvalCase` (`eval/runCase.ts`) replays a recording through the real researcher and the real analysis (see [Evaluating the agent](#evaluating-the-agent)) |

There are no feed fixtures any more: the Bing fixtures were deleted with the engine. The GDELT tests build their bodies in code (a JSON index of fictional articles on `.example.com` hosts, among them a title with a raw control character and one with a stray backslash), the provider search tests script the reply of `generateText`, and the cool-down after a 429 is tested with a fake clock and a fake queue (after a 429 a search fails at once; the first search after the pause asks again; no search asks after the third refusal; a timeout is not asked again). The guarded fetch is tested with a scripted transport and a fake address lookup, so it needs no local server either. Run the suites from `Servers`:

```bash
npx jest services/webResearch services/vendorResearch
```

`ts-jest` runs with diagnostics off and `tsc` does not check the tests under `services/`, so type-check them with a scratch `tsconfig` that includes `services/webResearch` and `services/vendorResearch`.
