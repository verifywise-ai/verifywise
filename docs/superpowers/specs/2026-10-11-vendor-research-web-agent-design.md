# Vendor research agent — web research agent (delta)

**Status:** awaiting review (revision 2) · **Date:** 2026-10-11 · **Branch:** `feature/vendor-agents-and-risk-page`

This document changes [the 2026-10-10 design](2026-10-10-vendor-research-agent-design.md). Where the two disagree, this one wins. Sections that are not mentioned here stay as they were: the findings and runs tables (apart from §11), the triggers, the cooldown and daily cap, accept and dismiss, the notification and the findings section of the UI.

**Update, 2026-10-31.** The Bing feed described below was removed (Q21 of that design). A run now searches with the engine of its research key: Claude web search for an Anthropic key and the GDELT news index for every other key. §2, §4, §6, §14 and §20 say so where they speak of Bing; the rest of this document is as of 2026-10-11.

**Later design.** The copies of official lists (the CISA catalog of known exploited vulnerabilities and the OFAC, UK and EU sanctions lists) and the credibility label that the code gives each finding from its sources are designed in [the vendor risk database design](2026-10-29-vendor-risk-database-design.md) of 2026-10-29, and, since 2026-10-31, always on (the flag was removed). Where that design changes how the records of public databases are read or what a finding's confidence means, it wins over this one.

## 1. Why this changes

The first design searched through a third-party search API (Tavily). That needs an extra account, an API key in the environment and a setup step, and an organisation without it sees "Vendor research is not set up".

The product owner's requirement, in one sentence: **whichever LLM key the organisation puts in, the agent searches the internet on its own and brings back information.** No third-party provider, no search key, no setup beyond the LLM key.

So the research stage becomes a real agent: a loop in which the organisation's own model decides what to search for and which pages to read, using two actions that our code implements, `search` and `read`, until it has enough or runs out of budget. Everything after the agent (the structured analysis, quote checking, de-duplication, caps, accept and dismiss) is the pipeline that exists today.

## 2. Decisions

| Decision | Choice |
|---|---|
| Search provider | None of our own: no Tavily, no provider API of ours, no search key, no search environment variable. **Since 2026-10-31 (Q21):** the search of the research key's own provider when it has one that is built (Claude web search for an Anthropic key, about $10 per 1,000 searches), else the GDELT Project's news index (the news of the last 3 months, free, with the project credited). Bing is removed. |
| Which models | Any model the app can already call for structured output (`generateObjectWithSelfCorrection`: OpenAI, Anthropic, DeepSeek, Custom endpoints, local models). The loop asks the model for its next step as JSON, so it does **not** need function calling. A model that cannot answer in JSON fails the run with a clear message. Checked on 2026-10-11 with a Custom key that points at DeepSeek. |
| Web access | Two actions written in our code: `search` (the news for most keys, the web and the news for an Anthropic key, through the engine of the research key) and `read` (any public page). §6. |
| What can be cited | Only text that an action returned in this run: result snippets and page excerpts. The model's own knowledge is never evidence. The "model knowledge, unverified" lane considered earlier is dropped, and with it a `basis` column. |
| "Not set up" | Only when the organisation has no LLM key. |
| Auto-run | Unchanged: on by default, `VENDOR_RESEARCH_AUTO_RUN=false` turns it off. It no longer waits for a search setup, so every new vendor in an organisation with an LLM key costs one run on that key, bounded by the daily cap (§15). |
| Politeness | The agent says who it is (`VerifyWiseResearchBot`), obeys `robots.txt` when it reads a page, and does not imitate a browser. |

## 4. What the probes showed (2026-10-11, from a developer machine)

There is no web search without a search engine, so the question is which engine answers a client that says who it is, without a key and without imitating a browser.

| Source | Result | Used? |
|---|---|---|
| Bing web search RSS (`/search?q=…&format=rss`) | 200 for an identified client. About 10 results with title, direct URL and snippet. | Used until 2026-10-31, then removed (§14) |
| Bing News RSS (`/news/search?…&format=rss`) | 200. Items also carry `pubDate`; the link wraps the publisher URL in an `apiclick.aspx?…&url=` parameter. | Used until 2026-10-31, then removed (§14) |
| DuckDuckGo (HTML and lite) | Challenge page (HTTP 202, no results) for an identified client and for a "compatible" bot User-Agent. It answers only browser-like clients; imitating one is bot-detection evasion. | No |
| Brave | One 200, then 429 on the next request. Too unreliable. | No |
| Yahoo, Ecosia, Startpage, Mojeek, Marginalia | 500, 403, no results, 403, time-out. | No |
| Google News RSS | Article links are JavaScript redirect pages that cannot be read or cited. | No |
| GDELT DOC API | 12 to 17 seconds and no articles for two test queries on 2026-10-11. | No then; **yes since 2026-10-31** (§6): one request per run, news only, 3 months |
| Vendor pages, `security.txt`, Wikipedia, publisher articles | Read fine. | Yes, `read` |
| Some publishers (BleepingComputer: Cloudflare 403) | Blocked. | "Blocked" is a normal outcome (§10) |

Facts to be honest about: Bing's `robots.txt` disallows `/search` (it does not mention `/news/search`), and Bing's terms do not give automated access to result pages. Worse, every feed carries a copyright notice that limits its results to personal, non-commercial display in an RSS reader and asks for Microsoft's written permission for any other use. Using the feed inside a commercial product and passing the results to an LLM provider is outside that notice. That is why the engine sat behind `SearchEngine`, and why §14 had a release gate. **Resolved on 2026-10-31 (Q21): the feed was removed.** See §14 and §20.

## 5. Architecture

```
Vendor created (auto) ─┐
"Research risks" ──────┴─ create run (queued) · enqueue `vendor_research`                  [own queue since phase 3]
        ▼
 worker: runVendorResearch
   1. mark running · target (name, domain, provides) · the organisation's model             [unchanged]
   2. RESEARCH LOOP, at most 24 steps and 5 minutes                                         [new]
        ask the model for the next step as JSON ── search | read | finish
        run it in code ── search: the engine of the research key (Claude web search or GDELT news) · read: guarded GET of a public page
        show the result back, repeat
        every snippet and excerpt goes to a ledger, tagged with a category
   3. evidence pack from the ledger (S1…Sn, at most 100 KB)                                 [changed]
   4. ANALYSIS  one structured call over the pack only, as today                            [prompt changed]
   5. validation · confidence ceiling · de-duplication · caps                               [unchanged]
   6. one transaction: findings + run                                                       [unchanged]
   7. auto run with findings: notify the assignee                                           [unchanged]
```

The loop only collects. It never writes findings. The analysis step sees a fixed snapshot of text, and its quotes are checked by code against that text. A hostile page can mislead the browsing step at most into reading more public pages (§7); it cannot write to the register.

**Why a JSON step and not native tool calling:** function calling needs provider support (tools, `tool_choice`, parallel calls) that OpenAI-compatible Custom endpoints and small local models do not all have. A JSON step works with every model that can already answer the app's structured-output calls, goes through the same self-correcting wrapper, and lets us control exactly what the model sees at each step.

Code layout:

- `Servers/services/webResearch/` is a small reusable toolkit, so that later vendor agents can browse too: `publicUrl.ts` (URL and address policy), `guardedFetch.ts`, `robots.ts`, `pageText.ts`, `readPage.ts` (robots check, guarded fetch and page text in one reader), `webSearch.ts` (the `SearchEngine` interface, with `id`, `kinds` and `newsWindowMonths`, and the engine that falls back from one to another), `providerSearch.ts` (Claude web search) and `gdeltSearch.ts` (the GDELT news index), `webSession.ts` (budgets, provenance, lookback and the ledger), `promptText.ts` (escaping for prompts), `researchLoop.ts` (the generic loop).
- `Servers/services/vendorResearch/prompts.ts` holds the vendor-specific loop and analysis prompts; `pipeline.ts` replaces the search step with the loop.
- `PipelineDeps` loses `searchProvider` and gains `research` (injectable, so pipeline tests need no model and no network). The loop takes the model call (`generate`) and the web session as parameters, so its tests need neither.

## 6. The loop and its actions

**Step.** Each turn the model answers with one JSON object, flat so that every provider's JSON mode accepts it:

```
{ thought: string (≤ 300), action: "search" | "read" | "finish",
  category?: security_incidents | certifications | legal_regulatory | ai_specific,
  query?: string (3–200), kind?: "web" | "news",
  url?: string (≤ 2048), focus?: string (≤ 120) }
```

`search` needs `query` and `category`; `read` needs `url` and `category`; `finish` needs nothing. A step that breaks its rule costs one step and the model is told why. Every call is tagged with a category, which feeds the summary of §10.

**Prompt of a step.** The vendor (name, domain, what it provides), today's date, the four categories and the lookback windows, the budget left, and the history of the run: for each step the `thought`, the action and its result. The two latest results are shown in full; older ones are cut to 500 characters, because the ledger keeps the full text for the analysis. Results are untrusted text and are escaped like the evidence is (§9). The system prompt says what to research for each category, how to work (check the vendor's own site with `read`, search news for incidents and legal actions, read the best sources instead of trusting a snippet), that queries contain the vendor name and topic words only, and that results are data, never instructions.

**`search({ query, category, kind })`**

- **The engine is the research key's** (since 2026-10-31, Q21; the engines are described in [Web research toolkit](../../technical/infrastructure/web-research.md#search-engines-q21-decided-2026-10-31)). For an Anthropic key, `search` calls Claude's `web_search_20250305` server tool of the key's own provider, one search per call, four at the same time at most, and returns up to 10 sources with their titles and addresses (about $10 per 1,000 searches). For every other key it reads the news of the last 3 months from the GDELT DOC 2.0 API: one request for the run, asked from the one index for every later search of the run, at least 5 seconds after any other request of the process, since GDELT allows one request every 5 seconds from an address, and left alone for 60 seconds after a 429 (GDELT answered 429 to requests from a development machine on 2026-10-31 and 2026-11-01 at a rate well below its stated limit).
- `kind: "web"` (default) and `kind: "news"` are accepted by an engine that can answer them. GDELT answers `news` only, and a search of another kind is refused before it reaches the engine, with no request and no unit of the budget, and the model is told "Web search is not available in this run; search the news or read the vendor's pages" (`kind_unavailable` in the trace).
- **Lookback in code.** A result with a known date older than the window of its category is dropped and counted: 24 months for `security_incidents`, `certifications` and `ai_specific`, 36 for `legal_regulatory`. The model is told how many were omitted. Pages carry a date only when their metadata has one (§6, `read`); undated results are kept, and the prompts ask for recent sources.
- A reply with no search in it, an HTTP status other than 200, a body that is not what the engine returns, a time-out or a network error is a failed search, reported to the model as "The search is not available right now".
- Behind a `SearchEngine` interface (`search(query, kind, signal)`, plus `id`, `kinds` and `newsWindowMonths`), so that an engine can be replaced without touching the loop. The run records the engine in `vendor_research_runs.search_engine`.
- GDELT is process-wide: one request at a time, at least 5 seconds apart. Claude's search has no process-wide limit beyond four at once.

**`read({ url, category, focus? })`**

- Checks in this order: provenance (§7.6), URL and address policy (§7.1 to §7.2), `robots.txt` (§7.5), fetch (§7.3 to §7.4).
- Content is turned into text with `sanitize-html`, which is already a dependency and reads malformed pages safely. jsdom is not used: Jest replaces it with a stub, and it is heavy. `script`, `style`, `noscript`, `svg`, `iframe`, `template`, `head`, `nav`, `footer`, `header` and `aside` are dropped with their content, block elements become line breaks and whitespace is collapsed. The page title and a publication date (`article:published_time` and similar meta tags, JSON-LD `datePublished`, `time[datetime]`) are read from the raw HTML when present.
- **Excerpt.** At most 8,000 characters. Without `focus`, the start of the text. With `focus` (a few keywords), the start (first 1,000 characters) plus the paragraphs with the most keyword hits, in page order, joined by a visible gap marker. Quotes must not span a gap. There is no paging in the first version; phase 4 adds the parts of a long page (§21).
- **Links.** For a page on the vendor's own domain, up to 25 links on that domain whose text or path contains a security, trust, privacy, legal, terms, DPA, subprocessor, compliance, certification, AI, status or incident word, so the model can move from the home page to the right pages.
- Failure reasons the model sees: `not_allowed`, `blocked_by_robots`, `blocked_by_site` (401, 403 or 429; a challenge page that a site answers with 200 is not detected on a read, it reads as a page with little text), `not_found`, `needs_javascript` (almost no text in a large HTML page), `unsupported_type` (for example a Word file; a PDF is read since phase 4, §21), `unreachable`. The ledger records the reason for the summary of §10.

**`finish`** ends the loop. If the ledger is empty, or a category that can be researched has no call, the first `finish` is answered once with a reminder of what is missing; the second `finish` is final.

## 7. The page guard

`read` lets a model choose which URL the server requests, and the model reads text that attackers can write. That is a server-side request forgery surface, and the first design avoided it by never fetching. It is the main new risk, so the guard is a new module, not `utils/safeOutboundUrl.ts`: that helper lets private ranges through on purpose (on-prem MLflow and Jira servers) and cannot be reused for untrusted URLs. No new dependency is needed: `ip-address` in `package.json` is only an `overrides` entry, and Node's `net.BlockList` and `https.request` are enough. The Bing feed is requested through the same guarded fetch.

1. **URL policy.** `http` or `https` only; no user or password in the URL; port empty, 80 or 443; the host is a DNS name with at least two labels. An IP address in any notation is refused (the URL parser turns `2130706433` and `0x7f.1` into dotted decimal, and `net.isIP` then sees them). `localhost`, `*.localhost`, `*.local`, `*.internal` and `*.home.arpa` are refused. The fragment is dropped.
2. **Address policy, checked on the connection.** The request is made with `https.request` / `http.request` and a validating `lookup` hook, so the address that was checked is the address that is connected to (no gap for DNS rebinding). Every answer for the host must be public; one non-public answer refuses the host. Non-public means any of: `0.0.0.0/8`, `10.0.0.0/8`, `100.64.0.0/10`, `127.0.0.0/8`, `169.254.0.0/16`, `172.16.0.0/12`, `192.0.0.0/24`, `192.0.2.0/24`, `192.168.0.0/16`, `198.18.0.0/15`, `198.51.100.0/24`, `203.0.113.0/24`, `224.0.0.0/4`, `240.0.0.0/4`, `::/128`, `::1/128`, `::/96`, `::ffff:0:0/96` (blocked as a whole), `64:ff9b::/96`, `64:ff9b:1::/48`, `100::/64`, `2001:db8::/32`, `2002::/16`, `fc00::/7`, `fe80::/10`, `fec0::/10` (the deprecated site-local range, RFC 3879), `ff00::/8`. `::/96` (the deprecated IPv4-compatible form), `64:ff9b:1::/48` (local-use NAT64, RFC 8215; `64:ff9b::/96` does not cover it) and `2002::/16` (6to4) carry an IPv4 address inside them, so an AAAA record under one of them could reach an internal IPv4 address through a translator or a tunnel.
3. **Redirects.** Followed by hand, at most 4. Every hop goes through the URL policy, the address policy and `robots.txt` again. A redirect from https to http is refused.
4. **Response.** Status 200 only. Content type `text/html`, `application/xhtml+xml`, `text/plain`, `text/xml`, `application/xml` or `application/rss+xml`. The body is streamed and cut off at 2 MB after decompression (`gzip`, `deflate`, `br`). 12 seconds to the response headers, 20 seconds in all. No cookies, no credentials, no `Referer`, TLS verification on. Character set from the header, then from a `<meta charset>` in the first 2 KB, then UTF-8.
5. **robots.txt (pages).** The group for `VerifyWiseResearchBot` if there is one, otherwise `*`; `Allow` and `Disallow` by longest match. A missing or refused file (404, 410, 401, 403 or 429) means allowed; any other answer (another 4xx, a 5xx, a network failure or a timeout) disallows the whole origin for the run. That is stricter than RFC 9309, which allows on any 4xx; it fails closed on purpose. Fetched through the same guard (5 seconds, 64 KB) and cached per host for the run. The search feed is the one declared exception (§14).
6. **Provenance.** A URL may be read only if, in this run, it was returned by `search`, or it is on the vendor's domain or a subdomain of it. Anything else is refused with a message that says to search first. So a page cannot send the agent to an arbitrary address with data in its query string.

## 8. Budgets and limits

| Limit | Value |
|---|---|
| Steps (model turns, including invalid ones) | 24 |
| `search` actions | 8 |
| `read` actions (successful or not) | 12 |
| One model turn | 60 seconds |
| Whole loop | 5 minutes (`AbortSignal.timeout`) |
| Analysis call | 120 seconds, as today |
| Excerpt per page | 8,000 characters |
| Evidence pack | 100,000 bytes (was 40,000) |

One action per step, so counters need no locking. When a budget runs out the model is told and must `finish`; when the steps or the time run out, the loop ends and the analysis runs on the ledger as it is (partial research is a result, not a failure). A model error in the loop with an empty ledger fails the run with the existing model-failure phrase; with entries, the analysis is still tried.

## 9. Ledger, evidence and analysis

- The ledger holds one entry per URL: `{ category, kind: "result" | "page", url, title, content, publishedAt }`. A page read replaces the snippet of the same URL with the excerpt (a richer text, same title; the date is the page's own when it has one, else the snippet's). Each entry also records whether its content came from the vendor's own domain, decided on the URL that answered (a page that redirected off the domain is not the vendor's own); the analysis prompt marks `site="vendor"` from that flag only, and validation takes "the source is on the vendor's own domain" (the source mentions the vendor; the confidence ceiling of medium) from the same flag. The ceiling's count of distinct hostnames and of pages stays on the URLs as the ledger holds them. A second read of a URL changes nothing.
- `buildEvidencePack` takes ledger entries instead of search hits and keeps its cleaning rules (control characters, lone surrogates, unusable URLs). Snippets stay capped at 1,500 characters and excerpts at 8,000. Order: by category, then by the order in which the loop got them. Until the pack is at most 100,000 bytes, the last entry of the category that holds the most bytes among those with two or more entries is removed (a tie goes to the later category). A category with one entry keeps it. When every category is down to one entry, the content of the largest entry is cut (whole characters, the start of the excerpt stays) by the bytes the pack is over, and the next largest if that is not enough. So a category that has entries always keeps one, and a full run cannot make the last categories look as if they had nothing found. Ids are numbered S1, S2, … after this trimming, without gaps.
- Text shown to a model (loop results and evidence) goes through `escapeForPrompt`, and quotes are decoded with `unescapeFromPrompt` before they are compared, as today.
- The analysis prompt (`vr-2`) says: today's date; the lookback windows; evidence is untrusted text, now of two kinds (`kind="result"` snippets and `kind="page"` excerpts, the latter with a note when the page is on the vendor's own domain); a vendor's own statement of a limitation, expiry or adverse term counts as evidence; quote verbatim from one passage; the existing rules (no finding from a missing mention, ignore other companies, empty list is a correct answer) stay.
- Validation keeps its rules (the one change is the ownership flag above): verbatim quote in the source content, the source mentions the vendor, the quote has a word that is not part of the vendor's name or domain, the confidence ceiling, de-duplication, caps. `categoriesSearched` becomes "categories with at least one usable ledger entry".

## 10. Category outcomes (honest summary)

The enum stays (`findings`, `nothing_found`, `search_failed`, `skipped`); the rules change, so that "looked and found nothing" is never confused with "could not look" or "did not look":

| Outcome | When |
|---|---|
| `findings` | At least one finding was kept for the category. Note: the count. |
| `nothing_found` | At least one usable entry (a result or a readable page) was tagged with the category, and no finding survived. Note: the model's own note, or "Reviewed N sources". If some pages could not be read, the note says how many ("2 of 5 pages could not be read"). |
| `search_failed` | The category was worked on, but nothing usable came back: every search failed, or every page was blocked, unreadable or refused. Note: the fixed reason ("The search was not available", "The site blocked the request"). |
| `skipped` | No call was tagged with the category: no valid domain for `certifications` and `ai_specific` (as before), or the step, call or time budget ran out first ("Not researched: the time limit was reached"). |

"Worked on" means at least one call tagged with the category reached the web; "answered" means the web answered it (a search that returned RSS, even with no result, or a page that was fetched). A category is `search_failed` when it was worked on and no call was answered. A call that the rules refuse before it reaches the web (a budget, a URL that is not allowed, an invalid step) is not work on a category.

The notes are a closed set of English phrases, because the UI maps each one to a translated sentence (and shows nothing it does not know):

| Outcome | Stored note |
|---|---|
| `findings` | `1 potential risk found`, `N potential risks found` (as before) |
| `nothing_found` | `No risks found in the sources reviewed`; `No risks found; N of M pages could not be read` (when any page call of the category failed); `Possible risks were found but could not be verified or are already recorded` (as before); the model's own note, shown as unverified, only when no page failed and the model proposed nothing |
| `search_failed` | `The search was not available` (every call of the category was a failed search); `The pages could not be read` (otherwise) |
| `skipped` | `Vendor website is missing or not a valid domain` (as before); `Not researched: the time limit was reached`; `Not researched: the research ended before this category was covered` |

A run is `failed` when there is no key, when the model fails, or when the web never answered the loop: either every call failed (`The run stopped because the web could not be reached`) or the model never searched or read (`The model did not use the research actions`). A run whose calls were answered but returned nothing is `completed` with no findings, and the analysis call is skipped because there is nothing to read. Otherwise a run is `completed`, even when every category says `nothing_found`.

## 14. Security and privacy

- **Egress.** The customer's server now talks to the public internet during a run: `api.gdeltproject.org` (queries with the vendor name and topic words; the search of Claude goes to the LLM provider of the key instead), the vendor's site, and the sites of articles. Every request names the bot. The LLM provider receives the vendor name, domain, the "what it provides" text and the page text. An air-gapped installation cannot use the feature: runs fail with "the web could not be reached".
- **The search: the release gate is closed (2026-10-31).** The Bing feed of the first version was removed: its `robots.txt` disallows `/search`, each feed's copyright notice limits the results to personal, non-commercial display in an RSS reader and asks for Microsoft's written permission for any other use, the Microsoft Services Agreement bars it, and the licensed route was retired on 2025-08-11. A run now searches with Claude web search (an Anthropic key; the provider is the processor of the queries, as it is of the rest of the run) or with the GDELT news index (every other key; commercial use is free if the project is cited, and the run summary cites it). If a search fails, the run says so (§10) and invents nothing. Pages are different: `robots.txt` is obeyed (§7.5).
- **Prompt injection.** The loop has no tools of its own: the model can only name a search or a URL, and code decides. GET only; public addresses only (§7.2); provenance (§7.6); no secrets or organisation data in its context; hard budgets; the analysis has no actions and its output is schema-bound and checked against the text; nothing reaches the register without a person accepting.
- **Stored third-party text.** Page excerpts and snippets are kept in `vendor_research_runs.evidence` as an audit trail (up to 100 KB per run). The UI shows only the quotes (300 characters) and links. Pruning old evidence stays out of scope.
- **Tenant isolation.** Unchanged: every query and job payload carries `organization_id`.

## 15. Cost

A typical run is 8 to 16 steps. Each step sends the prompt, the history (two results in full, the rest cut) and the budget, about 6,000 to 8,000 input tokens, so the loop reads roughly 60,000 to 130,000 input tokens in total, and the analysis another 20,000 to 30,000. On a DeepSeek-class price that is cents; on a frontier-model price it can be a dollar or more. The organisation pays it on its own key; the daily cap (default 50 runs) bounds it, and `VENDOR_RESEARCH_AUTO_RUN=false` removes the automatic part. These are estimates: `searches_used` and `pages_read` measure the tool side, and the provider's usage page the model side.

Long runs occupy a place of the research worker for up to about 7 minutes (5 for the loop, 2 for the analysis; since phase 3 the runs have a queue and a worker of their own, see "Architecture (phase 3)"). A burst of manual runs can therefore still leave the last one queued past the 15-minute stale limit, which ends it as "timed out" (the answer is **Research again**).

## 16. Testing

No unit test touches the network or a model.

- **Address and URL policy table:** `127.0.0.1`, `::1`, `::ffff:127.0.0.1`, `169.254.169.254`, `0.0.0.0`, decimal `2130706433`, hex `0x7f.1`, `10.0.0.5`, `192.168.1.1`, `100.64.0.1`, `fd00::1`, `fe80::1`, `localhost`, `a.localhost`, `printer.local`, `http://user:pw@example.com`, port 8080, `file:`, `ftp:`, and a public address that must pass (`93.184.216.34`).
- **Guarded fetch** (local HTTP server with an injectable address policy): a host that resolves to a private address, a redirect to a private address, a redirect loop, a https→http redirect, a body over the cap, a gzip bomb, a wrong content type, a slow response.
- **robots parser:** group choice, longest match, `Allow` over `Disallow`, wildcard and `$`, 404 and 500.
- **Page text:** boilerplate removed, title, date from the three sources, `focus` excerpt with gap markers, links only for vendor pages, JavaScript-only page detected.
- **Search:** no test reaches the network: the engines are tested with fakes (the GDELT index and the Claude search reply, built in the tests), lookback filtering by category, a body that is not what the engine returns, 429 and its pause, time-out, de-duplication. (The Bing fixtures of the first version were removed with the engine.)
- **Web session:** budgets, provenance rule, snippet replaced by excerpt, category tags, unusable URLs.
- **Research loop:** driven by a scripted `generate` (search, read, read a refused URL, an invalid step, finish with an empty ledger and the reminder, step limit, time limit, model error with and without entries, observation cutting). A test that runs the real `generateObjectWithSelfCorrection` against an AI SDK mock model checks the step schema.
- **Pipeline:** outcomes of §10 for every row, partial ledger, the failed-run rule, the evidence cap, a quote from a snippet and from a page excerpt, an excerpt with a gap marker.
- **Trigger, config, job, controller, routes, tenant isolation:** updated for §12; the old search-not-configured cases are removed.
- **Frontend:** not-set-up state, run summary, `search_failed` and `skipped` copy, de/fr/es strings.
- **Gates:** as in the first design (`tsc`, build, format-check, `i18n:audit:strict`, `check:api-drift`, touched suites).
- **End to end:** in a real browser as an end user, with the real LLM key and the real web: create a vendor with known public incidents, watch the auto run, read the findings and sources, accept one and dismiss one, check the risk in the register, the notification, the cooldown and the daily cap, and then remove the test data.

## 21. Performance work (2026-10-27)

The agent is now improved against measurements and not against single vendors. The ideas, their order and the rulings are in `docs/superpowers/plans/2026-10-27-vendor-research-agent-performance.md`; this section records what changes in the design.

**Measure first (phase 1).**

- **Run trace.** Each run stores a bounded record of what it did (`vendor_research_runs.trace`): the steps, the model calls with their tokens, the candidates that validation, de-duplication or the caps turned away, what was left out, and the time of each phase. It holds queries and addresses, so only administrators (`llmKeys.admin`) can read it, through `GET /api/vendors/:id/research/runs/:runId/trace`. The analysis was moved out of `pipeline.ts` into `analysis.ts` (`analyse`), so that the pipeline and the evaluation run the same code.
- **Dismissal reasons.** Two reasons are added, `wrong_vendor` and `outdated`, because a person who dismisses a finding because the sources were about another company, or were old, is telling us that the research failed and not that the risk does not matter. Every decision is counted (`vendor_research.finding.decisions`) and `GET /api/vendor-research/decision-stats` reports the rate of acceptance by prompt version and category.
- **Evaluation set.** `services/vendorResearch/eval/` replays recorded cases through the real researcher and the real analysis, scores them (precision, recall, irrelevant and duplicate sources, bad addresses, dated web results, snippet-only findings, overconfidence, repeated events, cost) and holds each case to targets. A target the agent does not meet yet is a declared gap that names the roadmap idea meant to fix it, and a test fails if a gap is met without its line being deleted or a target is missed without being a gap. `npm run eval:vendor-research` runs it, and `--live` runs one vendor for real.

The behaviour of the loop, the validation and the caps described in §6 to §10 is unchanged by phase 1.

**Quick wins (phase 2).** Each one is a rule in code, measured by a case of the evaluation set; the prompt version is `vr-3` for the whole phase.

- **One page, one entry.** An address is reduced to one spelling (`webResearch/urlCanon.ts`: tracking parameters, AMP and `m.` forms, fragments, default ports, trailing slashes). A page that names a canonical address (`rel=canonical`, `og:url`) is filed under it only when that address is the same document on the same site. Two pages with the same text get one entry, and the second read gives its budget unit back (at most three times a run). A search result that repeats an earlier one (same title and snippet) is left out.
- **No bad addresses.** An address that ends in a percent-encoded quotation mark or angle bracket is refused without a request ("the address is not valid").
- **Web results carry no date.** The web feed dates a result by the day it was crawled, so the date is used as an upper bound for the lookback only and is never kept or shown. News dates and a page's own date are kept.
- **Relevance in code.** A result whose title, snippet and address name neither the vendor nor its domain never enters the ledger (`vendorResearch/identity.ts`, shared with the validation). The model is told how many results were left out and why.
- **Repeated queries.** A query whose words are those of an earlier query of the same feed (Jaccard 0.8 or more) is refused without using budget.
- **Short queries.** The search is made with the vendor's name and at most three topic words (`vendorResearch/queries.ts`: `normalizeQuery`); operators, boolean words, addresses and small words are removed, and the model is told what was searched when that differs from what it wrote. The loop task suggests the queries that work for the two news categories.
- **A check of the website before the loop.** One guarded read of the vendor's home page, outside the budget and the ledger, tells the model whether the site can be read, whether the page names the vendor and which security, trust, privacy and legal pages it links to (a `<briefing>` block, data like a result). A site that does not answer, or that the `robots.txt`, the site or the address policy refuses, is closed for the run: reads of its pages are refused without a request, and the two categories that need the website read as "The pages could not be read". A home page that does not name the vendor is a warning to the model, not a rule of the code.
- **Budgets, from five live runs.** The limits stay (8 searches, 12 reads, 24 steps). A read that failed gives its unit back (at most six a run), a page that failed for good is not tried again, and a site that moved (the recorded domain redirects to a domain of the same brand whose home page names the vendor) is the vendor's website under its new domain. The loop prompt tells the model to move on after two empty searches of a category.
- **One retry of a failed search.** A search that failed for a reason that passes (a network error, a time-out, a 5xx, or a 429 that asks to wait 5 seconds or less) is asked of the feed once more by the engine; the session sees one answer or one error. Searches are counted by feed and outcome, and retries by feed (`vendor_research_searches_total`, `vendor_research_search_retries_total`).
- **A cache that runs share.** The `robots.txt` of a site (24 hours, the most RFC 9309 allows), the text of a page (15 minutes) and the answer of a search (10 minutes) are kept in Redis (`webResearch/webCache.ts`), so a second run of a vendor, or two vendors on one platform, ask the web for less. A hit costs no request and no wait in the search queue but still counts against the run's budgets. Only what worked is kept; a Redis that is down, slow or not ready is a miss and never a failure; the keys are hashes and name no organization, since the content is public and fetched the same for everyone. Lookups are counted by kind and outcome (`vendor_research_cache_total`). The evaluation harness passes no cache, so a live evaluation measures the web.
- **Confidence by source.** `high` confidence no longer means two hostnames. `vendorResearch/sourceTiers.ts` gives every cited source a tier (the vendor's own site, a regulator or a court, a major publisher, an aggregator, other) and a publisher (the name of the site, so `bbc.co.uk` and `bbc.com` are one), and the ceiling is `high` only for two independent publishers of which one is credible. All pages of the vendor's own site are one publisher, and an aggregator is none, so a story and its copy are one source. The analysis prompt states the rule to the model. The case of one story on two domains of one publisher (gap 25) now passes.
- **Anchored ratings and a reason.** The analysis prompt defines each value of the likelihood and the severity by what the sources show and by the effect on the company (so two runs rate alike), tells the model to rate this vendor's evidence and not the worst case, and asks for a `rationale` per finding: one sentence on why the two ratings are what they are. The sentence is stored (`vendor_risk_findings.rationale`, nullable) and shown in the finding row under "Why this rating", so the person who decides can see the reasoning before accepting. Nothing in the code reads it.
- **Materiality.** Three answers of the vendor's scorecard (data sensitivity, business criticality, regulatory exposure), taken only when they are values of the vendor form, go into the analysis prompt as a `<materiality>` block and are used to judge the severity and the order of the risks, never the likelihood. The research loop does not get them, so nothing of the company's dependence on the vendor reaches a web search. The answers go to the organization's own LLM provider with the evidence.
- **A key for each job.** An Admin can choose one LLM key for the research loop (many small calls: a fast, inexpensive model is enough) and another for the analysis (one large call: a stronger model can help), in **Research settings** on the findings section (`GET`/`PUT /api/vendor-research/settings`, `llmKeys.admin`, table `vendor_research_settings`, one row per organization). Nothing chosen means the newest key for both, which is what runs did before; a chosen key that is gone, or that is not the organization's, is the default again (a 404 on save), and a setting can never fail a run. The run's `model` column and each model call of the trace say which model did what. The fallback to plain JSON that the loop may learn is not carried to an analysis on another model.
- **Live progress.** A running run writes where it is (`vendor_research_runs.progress`, JSONB, null unless the run is running): the phase (`researching`, `analysing`), the turns of the loop, the latest action and category, the searches and pages so far and the categories worked on, with the time it was written. It holds counts and closed words only, so it is part of the run that every role reads, and the page shows it under "Researching…" ("Searching the web: Security incidents", "Researched so far: ...", "Searches: 3, pages read: 2"). The writes never fail or slow a run (the newest report replaces an older one that is waiting), and only a running run is written, so a late write cannot undo the end of a run. The two-minute polling window now counts from the latest sign of life, so a run that keeps moving is followed to its end, and one that has gone quiet is given up on.

**Architecture (phase 3).** The prompt version is `vr-4` for the whole phase.

- **Several actions in a step.** The model answers a turn with a thought and a list of up to four actions (`{thought, actions: [...]}`; the older single-action answer still parses). The loop runs them in order and sends the reads that follow one another to the web together (`WebSession.readMany`: checked and settled in the order of the step, fetched at once, at most two at a time from one host), so a model that puts independent searches and reads in one step saves model turns, which cost more than the web calls. A `finish` ends the step; actions beyond four are not run and the model is told. The trace keeps the model turn of each action (`turn`).
- **Routine work in code.** After the check of the website and before the first model turn, code makes the searches and the reads that every run needs (`vendorResearch/gather.ts`, switched on by `gather: true` of `createVendorResearcher`, which the job sets): the baseline news searches of the news categories (`<name> data breach`, `security incident`, `lawsuit`, `fined`), one more query for each of them from what the model remembers about the vendor (`vendorResearch/hints.ts`, idea 10: one cheap call started while the website is checked, a query only and never evidence), the best two results of each news category read in full (title names the vendor, then source tier, then date, different publishers first; idea 14), and for `certifications` and `ai_specific` the vendor's own pages that its home page links to and its `sitemap.xml` lists, ranked by the words of the address and of the link text (at most three per category; the pages that sites usually have, only for a category left with fewer than two). A closed site, a home page that redirected off the vendor's website and a home page that does not name the vendor are not crawled. The work goes through the web session (`searchMany`, `readMany`), so every rule of the session applies, but it is paid for apart (`setCodeBudget`, calls `by: "code"`, no refunds), so the model keeps its 8 searches, 12 reads and its refunds. The model is told what was collected in the briefing, and the prompt tells it not to repeat that work. The trace keeps the sitemap as a `gather` step and the rest as steps with `by: "code"`. The evaluation has a case for it (`gathered-sources`) and a case or a live run can say `gather: true`.
- **One loop for each category.** After the routine work, one loop for each category that the vendor allows runs at the same time (`vendorResearch/loops.ts`, `perCategory: true` of `createVendorResearcher`, which the job sets; idea 17): at most four model turns, a budget of its own cut from the model's 8 searches and 12 reads through `WebSession.pool` (a news category two searches, a category of the vendor's website one, and the reads shared out evenly: 3, 3, 2, 2 and 2; without a domain three loops with 3, 3 and 2 searches and 4 reads each), a task that names the one category (`You research one category only: <category>.`) and a briefing of what the code collected for that category only (the check of the website goes to the two categories that read the site). The first `finish` of a loop counts only the sources and calls of its own category, and with `allowEmptyFinish` an empty answer of calls the code made is an answer. The run ends as its loops do (time, then steps, then budget, then finished; a model error only when every loop failed), every loop is waited for before the researcher rejects, and the trace names the loop of every step and model call (`loop`). The evaluation has a case for it (`one-loop-per-category`, `perCategory: true`, steps recorded per category in `recording.loops`).
- **Events (idea 24).** The sources of the evidence pack that report one event form a cluster (`vendorResearch/clusters.ts`, by code, no model): both dated, of one kind of event (an intrusion, an outage, a lawsuit, an enforcement; read from the title and the first 300 characters, and from the title alone for a page of the vendor's own site), within 21 days of the first source of the event; or naming the same CVE id. The analysis prompt shows an event's sources together in an `<event id="E1">` element and asks for one finding for it; the de-duplication then keeps the first (the most severe) candidate of an event and drops a later one that cites only sources of events a kept candidate cites (`duplicate.same_event` in the trace). The evaluation case `one-event-three-findings` no longer has gaps.
- **Check of the findings that rest on snippets (idea 28).** After the caps, a finding whose cited sources are all search results (none a page the research read) has the page of its best source read with the page reader of the run (`vendorResearch/verifySnippets.ts`, called by `analyse`): the most credible source first (the tier of `sourceTiers.ts`), the next when a page cannot be read, two pages at most for a finding and one deadline of 20 seconds. A page that holds the quote confirms the finding; one that does not marks it `snippet_only` (a new column of `vendor_risk_findings`) and lowers its confidence to `low`; when no page can be read it is marked and keeps its confidence. The finding is kept either way, the confidence is never raised, and the findings list tells the person that the quotes come from search results. The reads are in the trace (phase `verification`, steps `by: "verification"`); the case `quote-not-on-the-page` and the closed gap of `snippet-only-quotes` pin it.
- **Verifier (idea 29).** After the caps, one more model call reads all the findings that stay, with the claim, the impact and the address, date, title and quote of every source they cite and no other web text (`vendorResearch/verifier.ts`, called by `analyse` with the model of the analysis, at the same time as the reads of the check above; 30 seconds). It answers three questions with true or false for each finding: `same_company`, `quote_supports_claim` and `source_in_window`, and is told to answer true when it cannot tell. A finding with a false answer is not stored and the trace counts it as `verifier.other_company`, `verifier.not_supported` or `verifier.out_of_window` (once, under the first question it failed). A finding with no verdict is kept, and so is every finding when the call fails (timeout, error, an answer that does not fit the schema): the call is recorded as failed (`purpose: "verifier"`, `ok: false`) without its error message. It is off in `analyse` and `runVendorResearch` unless `verifier: true`; the job and live evaluations turn it on. The evaluation can replay it (`verifier` in a case and in a recording) and has the case `verifier-drops-findings`.
- **A queue and a worker of its own (idea 34).** The research runs left the queue of the automations (`vendor-research` instead of `automation-actions`; the job is still `vendor_research`, with the id, the options and the retry of before). `vendorResearch/queue.ts` holds the queue and the producer, `vendorResearch/worker.ts` the worker, which `jobs/worker.ts` starts with the others and which refuses a job of any other name. It carries out `VENDOR_RESEARCH_WORKER_CONCURRENCY` runs at a time for each process (5 unless set; the one setting the worker reads). A run holds a place for minutes while every other job is short, so on the shared queue a burst of runs held up the notifications, the recomputes and the reports, a long line of other jobs could leave a run queued past the 15 minutes, and the empty-the-queue (`obliterate`) that the backend does to the automation queue each time it starts lost the runs that were waiting. The research queue is never emptied. A job that an older backend adds to the automation queue after the upgrade finds no handler there and fails; its run ends as `timed out` by the stale rule, as a run whose job was lost always did.

**Coverage (phase 4).** The prompt version is `vr-5` for the whole phase.

- **Parts of a long page (idea 22).** A page that does not fit in one excerpt is cut into parts of at most 8,000 characters (`pageParts` in `pageText.ts`: the cuts fall at a paragraph, a line or a word past the middle of the window, never inside a surrogate pair; at most 40 parts), and the result of a read says how many parts there are. A `read` with `part` (from 1) shows another one. The session holds the text of the pages it read (`heldPages`), so a part is no request, takes no unit of the budget of reads and has no call record. A number outside the parts, a part that was already shown and a part beyond the first two extra parts are refused with a reason (`no_such_part`, `already_read`, `parts_limit`). The two parts that are shown first are merged into the ledger content of the page behind a gap marker, so a page source holds at most 24,010 characters (`MAX_PAGE_CONTENT_CHARS`) and the model is shown only what the evidence holds: a quote it takes from a part is a quote the validation can find. The step of the trace carries `part`. The evaluation set has a case for it (`long-policy-part`: a clause in section 15 of a policy of 30,000 characters).
- **PDFs (idea 20).** The page reader reads a PDF (a data processing agreement, a SOC 2 letter, a white paper) into text, a title and a date. `guardedFetch` gets a limit by media type (`maxBytesByType`), and the reader asks for 10 MiB for `application/pdf` and `application/x-pdf`, and for `application/octet-stream` and `binary/octet-stream` too when the path of the address ends in `.pdf` (the file must begin with `%PDF-`); every other type keeps 2 MiB. `pdfText.ts` gives the bytes to `pdf-parse` in a worker thread of its own (`readPdf`: 256 MiB of heap, 20 seconds, the first 100 pages, at most 320,000 characters, at most 2 files at the same time in the process, the library's evaluation of font programs off), ends the thread when a limit is passed or the caller gives up, and turns the lines of print into paragraphs (`reflowPdfPage`) so that `focus` and the parts of a long page work as for HTML. Title: the document's own, else the file name of the address. Date: the later of the creation and modification dates, believed only within 1993 and a day ahead. A scan with no text layer, a damaged or encrypted file, and a file that passes a limit are `unsupported_type` (a cancelled read is `unreachable`). The routine work of the code treats a PDF of the vendor's site as a page of its category, after a page of the same fit. A thread bounds time and memory and is not a sandbox. The worker is tested against the real library with a generated PDF; the evaluation set needs no case, because a recorded page is the same for the analysis whatever file it came from.
- **Pages that a script builds (idea 21).** A page of 20,000 characters or more with fewer than 500 characters of text (`looksLikeJavaScriptShell`) was `needs_javascript`. The reader now tries two things first. **The data the page carries** (`scriptedText.ts`, `extractScriptedText`; nothing runs): the `props.pageProps` of a Next.js page, JSON-LD blocks and `<noscript>` blocks, taking the prose in them (at least 25 characters and five words, mostly letters, no address, identifier, list of class names, code or "enable JavaScript" notice; markup in a string is turned into text; the keys that carry addresses, styles and images are skipped), once each, in page order, cut between sentences at 100,000 characters, with every part of it bounded because the page is a third party's. Then, only when `VENDOR_RESEARCH_HEADLESS` is `true` (the worker reads it; off by default), **a headless Chromium** (`renderPage.ts`, `createChromiumRenderer`; Playwright, which the PDF reports use already) given the document that was read. The browser never opens a socket for the page: every request is intercepted and fulfilled by `guardedFetch` (URL and address policy, `robots.txt`, redirects, limits) or refused, only `GET` requests for scripts and for the data of scripts are answered (3 MiB each, 60 requests and 12 MiB for a page), a second navigation of the page gets "no content", frames, windows, dialogs, downloads, service workers, permissions and web sockets are shut, and Chromium starts without name resolution (`--host-resolver-rules`) and without WebRTC's direct UDP. A render is at most 20 seconds, and at most 2 run at once in a process (`limiter.ts`, which the PDF reader shares). The browser starts on the first page that needs it, closes after a minute idle, and a launch that failed is logged once and not tried for 5 minutes. As root Chromium is started without its own sandbox (as for the PDF reports). Any failure, or a rendered page that still holds fewer than 500 characters, is `needs_javascript` as before. `sharedPageRenderer` (`vendorResearch/pageRenderer.ts`) gives the jobs of a worker one browser; `createVendorResearcher({ render })` hands it to the page reader of each run. A browser bounds time and memory and the guard bounds what it reaches; neither makes the code of a page harmless. The renderer is tested against a scripted stand-in for the browser, and was checked once against a real Chrome with a page that builds its text and one that tries to open a frame, post data, redirect and reach a name the guard refuses; the evaluation set needs no case, because the analysis sees the same page text whichever way it was got.
- **Other names and the identity profile of the home page (idea 9).** The record of a vendor has one name and the press may use another ("Meta Platforms" is "Facebook"), so a source that names the vendor only by that other name was taken for a source about someone else. A target now carries `aliases`, and the matcher of `identity.ts` reads each one like the name (as written, and without the legal form). They come from two places. **A person** writes them in the *Other names* field of the vendor (`vendors.other_names`, TEXT, optional; names separated by commas, semicolons or line breaks, stored as "A, B"; at most 500 characters, 8 names, 2 to 80 characters each, validated by `VENDOR_VALIDATION_LIMITS.OTHER_NAMES`, which the research reads too). **The home page** gives the names its site uses for itself: `siteIdentity.ts` (`extractPageIdentity`) reads `og:site_name`, `application-name`, the JSON-LD nodes of an organization type and of a `WebSite` (their own `name`, `alternateName` and `legalName` only) and the JSON-LD product nodes, without running anything, and the page reader puts the result on the fetched page (`identity`) and in the shared cache. `profileOf` (`aliases.ts`, called by `checkWebsite`) adopts a name only when the page names the vendor and is the vendor's own site, and only when the name is built around the first word of the vendor's name or the brand of its domain (a part of the recorded name is left out unless it is the brand of the domain; at most 4 names); products (at most 5) are text of the briefing and never names. The person's names come first, the site's after, at most 8 together (`withAliases`). They reach the matcher of the session, `normalizeQuery` (a query that names the vendor only by an other name leads with it), `suggestedQueries` (one more query for each news category), `hintSearchesOf`, the focus of the articles of `gather.ts` and `planNewsReads`, the prompts of the loop, the hints, the analysis and the verifier (`<also_known_as>`), and, through `ResearchResult.siteNames`, the analysis of the pipeline, so that the validation and the verifier accept a source that the search let in by an other name. The trace is unchanged: it holds no text that a page wrote. See [web-research](../../technical/infrastructure/web-research.md#the-names-a-vendor-is-known-by) and [vendors](../../technical/domains/vendors.md#other-names).
- **News in the language of the vendor's market (idea 11).** The news feed answers a query in the language it is written in, and the press of a vendor in Germany, France or Italy writes in German, French or Italian first (the data protection authority tells what it fined in its own language), so a vendor whose market is known is searched in that language as well (`vendorResearch/market.ts`). The market is read from the record of the vendor and from nothing a page wrote: the country domain of its website (`.de` and `.at` German; `.fr`; `.it`; `.es`; `.nl`; `.pt` Portuguese of Portugal; `.br` Portuguese of Brazil), else the legal form at the end of a name of two words or more (`GmbH`, `AG`, `UG`, `KG`; `SAS`, `SASU`, `SARL`; `S.r.l.`, `S.p.A.`; `S.L.`, `SLU`; `B.V.`, `N.V.`; `Lda`; `Ltda`), the country domain winning. `.com`, `.io`, `.ch`, `.be` and the like, and `S.A.`, `Inc.` and `Ltd`, say no market, and such a vendor is searched in English only. For each news category (`security_incidents`, `legal_regulatory`) `localQueries` gives two queries, the name without its legal form and at most three topic words (the breach and the incident; the fine, with the name of the authority, and the lawsuit). `suggestedQueries` adds them last, after the English queries and the query of the first other name, so the routine work (`planSearches`, which labels each with its language), the hints and the task all share them. The code pays for them (up to 12 routine searches for a vendor with an other name and a market) and the briefing names the language (`Brume Logiciels CNIL sanction (French)`). The feed is not asked for a market (`mkt`): measured on 2026-10-28, a query in the local language already returns local news, and `mkt=de-DE` and `mkt=es-ES` returned nothing for queries that return results without it (ruling R33). The prompts say that a source may be in another language, that the finding is written in English and its quote kept as written, and that the verifier judges a quote in the language it is written in; the national data protection authorities (the CNIL, the Garante, the AEPD, the Autoriteit Persoonsgegevens, the CNPD, the ANPD) are regulators in `sourceTiers.ts`. The trace is unchanged (the language of an action is not one of the fields it keeps). Limit: the event clusters read English words, so an English and a French article about one event are not one cluster in code; the rule of the prompt that one event is one finding covers it. See [web-research](../../technical/infrastructure/web-research.md#the-news-in-the-vendors-language).
- **Records of public databases (idea 30).** Three public databases hold facts that the press often only repeats, and they can be asked directly with the name and the domain of the vendor: the CISA catalog of known exploited vulnerabilities, the National Vulnerability Database (the critical vulnerabilities, CVSS 9.0 or more, of the last 119 days, for the products of one CPE vendor) and Have I Been Pwned (the breaches of a service on the vendor's domain). The code looks the vendor up before the first model turn, at no cost of the model's budget, and each record that matches enters the ledger as a source that was read (`WebSession.addRecords`: a page, not a search result; dated; the lookback of the category applies; a read of its address is refused as `already_read`), at a public address that shows it, with the database's own words as its text. A record is the vendor's only when the string the database uses for the vendor is a name of the vendor letter for letter (its name and other names, each with and without the legal form, and the brand of its domain, as letters and digits only), never when it merely contains or begins with it; the NVD matches the CPE vendor whole. At most 5, 3 and 3 records (the newest; the NVD the highest score), a CVE in the catalog and the NVD is one source. `cisa.gov` and `nvd.nist.gov` are government hosts and so the tier of a regulator, Have I Been Pwned is `other`; its data is licensed under CC BY 4.0 and every record names it. The prompts say what a record is, and that a record of a vulnerability is about a flaw in a product and not about a breach of the vendor's own systems. The lookups share 8,000 ms, are kept in the memory of the process (30 minutes for the catalog, 6 hours for the others), the NVD is asked at most four times in 30 seconds, a database that failed is left alone for 5 minutes, and `VENDOR_RESEARCH_RECORDS=false` turns the lookup off. Each lookup is a step of the trace (`gather`) with no text of a record. See [web-research](../../technical/infrastructure/web-research.md#records-of-public-databases).
- **The filings of the SEC and the regulator in the query (idea 31).** A listed company that has a material cybersecurity incident has to report it to its investors in a Form 8-K under Item 1.05 within four business days (since December 2023), and that filing is the vendor's own statement of an incident in its own systems. The records of public databases get a fourth source: the code reads the list of registrants of the SEC (the same file for everyone, so nothing about the vendor is sent), picks the registrant whose name is a name of the vendor (the names alone, never the brand of the domain; entries of one CIK are one registrant, entries of different CIKs leave the vendor with nothing), asks for its recent filings by its CIK, and keeps the Form 8-K and 8-K/A that report Item 1.05, at most 3, the newest, inside the lookback. Each is a record at the main document of the filing in the archive, with the facts and the text of Item 1.05 (2,500 characters at most) read through the run's page reader, so `robots.txt`, the guard and the cache apply; a filing that cannot be read is a record of its facts alone. The tier is that of a regulator, the prompts say what a record of the SEC is, the lookups share the 8,000 ms and the off switch of the other databases, and the memory keeps the list for a day, the filings of a registrant for an hour and the text of a filing for a day (ruling R35; litigation is not read). The regulator `site:` searches of the first plan became news queries that name the authority: for a vendor with no market of another language, `FTC` and `settlement` (the default), `ICO fine` for a `.uk` domain, `DPC fine` for `.ie`, `OAIC` for `.au`, after the English queries (`regulatorTopicsOf`; measured on the news feed on 2026-10-28). See [web-research](../../technical/infrastructure/web-research.md#the-regulator-in-the-query) and [records](../../technical/infrastructure/web-research.md#records-of-public-databases).
- **Availability: outage news and the status page (idea 32).** A fifth category, `availability` (an outage or a lasting degradation of the vendor's service that affected its customers, or a pattern of them; lookback 12 months), is researched like the other news categories: one more news query, `<name> outage` (in English for every market; the query of an other name and the hints as for the others), a loop of its own, and the same ledger, rules and verification; a vendor without a domain is researched in the three news categories. The vendor's own status page is a second source: the code reads the Atom feed `/history.atom` that a Statuspage or incident.io status page offers as its subscription feed, at `status.<domain>`, `<brand>.statuspage.io` and `<brand>status.com` (a feed on the last two is the vendor's only when its title holds a name of the vendor), with the `robots.txt` check of the page reader (`records/feedFetch.ts`), and gives the run a summary (entries, incidents of the window, planned maintenances) and the three newest incidents with their updates, as records of the category `availability`. Each source of the records layer is now a record of one category (`RECORD_CATEGORY`), asked only when the run researches that category, with the lookback of that category, and a loop is told only of the records of its own category. The JSON API of Statuspage is not used, because the `robots.txt` of the status pages that were probed (GitHub, Datadog, Atlassian) disallows `/api/` and `/embed/` for every robot; a planned maintenance is counted and never a record; a vendor with no status page, or whose host does not answer, gets nothing, and that is no failure. The feed comes from a host that the vendor may not control, so it is read in time proportional to its size whatever it holds (the root is read by hand, the tags of a link reach to the next `<` at most, the white space around a label is bounded, and the text of an update is made by the page reader's `htmlToText`; the tests feed the parser feeds made to be slow). A finding that cites one record of a status page is capped at `low` (one page that is not the vendor's own site), `medium` with two incidents, `high` only with a second publisher that is credible. One migration widens the CHECK on `vendor_risk_findings.category` for `availability` and `financial_health`; the client has the category and its label in English, German, French and Spanish. Eval case 19 `status-page-incident-history`. `PROMPT_VERSION` stays `vr-5`. See [web-research](../../technical/infrastructure/web-research.md#records-of-public-databases).
- **Source memory and the scheduled scan (idea 37).** Research can be repeated on a schedule without asking the model again about what it has already seen. Every completed run records the sources of its evidence pack in `vendor_research_sources` (the key is the address alone, `sourceKey`: the site without `www.`, the path without the marks of other forms of the same document, and the query), after the transaction that stores the findings has committed; a run that failed remembers nothing. A **scheduled** run (a new trigger, `scheduled`) researches the vendor in full, then sets apart the sources it finds in the memory, so that the pack, the analysis and the validation see only the new ones, a category without a new source says `No new sources since the last run`, and a run where nothing is new ends without a model call; a manual or an automatic run ignores the memory. The first scheduled run of a vendor has no memory and is a full one, nothing is backfilled and nothing is pruned, and a page that changes at a known address is not analysed again (the policy pages of the vendor itself are for the snapshots of idea 38). The scan is an hourly job (minute 17) of the research queue, registered at start by `jobs/producer.ts` and carried out by the research worker by the name of the job: for each organization whose Admin chose an interval (**Research settings**, Off by default, every week, every 2 weeks or every month, `vendor_research_settings.scan_interval_days`) it works while the runs of the last 24 hours are under half of the daily cap and starts at most 5 vendors that are due (researched longest ago first, no demo vendors) through `startVendorResearch`, so every check of a manual start applies but the cooldown. The assignee is told of the findings of a scheduled run as of an automatic run's. No environment variable and no new queue, and no prompt changed. See [web-research](../../technical/infrastructure/web-research.md) and [vendors](../../technical/domains/vendors.md#the-scheduled-scan).
- **The pages where the vendor states its terms (idea 38).** Every completed run keeps the text of the vendor's own policy pages that it read (its terms, privacy policy, data processing addendum, list of subprocessors and security page, found by their address or title) in `vendor_research_snapshots`, and the next run, of any kind, compares what it reads with what was kept. A page that changed becomes a source of its own: a ledger entry on the vendor's site, titled `Change to <title>`, in `certifications` (the security page) or `ai_specific`, whose text begins `Page change:` and lists the lines added and the lines removed, at an address made of the page's with `#changed-` and 8 characters of the hash of the new text, so that each change has an address of its own. The sources come first in their category and are set beside the memory of the sources, so a scheduled run whose memory knows the page still shows its change. The first visit only stores; the lines are compared as sets, without regard to case, with the stamps of a page (`Last updated`, `©`) left out, and a change of fewer than 40 characters keeps the new text and shows nothing. The researcher notes the pages by wrapping the reader of the session (the whole text, at most 8 documents for a run); the pages are written after the transaction that stores the findings has committed, for a run that completed only, and a page that no run has read for 365 days is forgotten. The model judges whether a change is a risk (one bullet of the system prompt: only an adverse term, a new subprocessor or AI provider, a weaker commitment or a lost certification). No environment variable, no endpoint, no change of the screen; `PROMPT_VERSION` is `vr-6`, for the whole of phase 5. See [web-research](../../technical/infrastructure/web-research.md#the-pages-where-the-vendor-states-its-terms) and [vendors](../../technical/domains/vendors.md#policy-page-changes).
- **The finances of the vendor and the sanctions list (idea 39).** Two sources of risk that the first five categories did not look for. **A sixth category, `financial_health`** (layoffs, a funding shortfall, insolvency or bankruptcy, or a sale or a change of control of the vendor, that threatens the continuity or the quality of its service; a funding round, growth or hiring is not a risk; lookback 12 months), is researched like the other news categories: three more news queries for every vendor (`<name> layoffs`, `<name> bankruptcy`, `<name> acquisition`, in English for every market, and `<other name> layoffs` for a vendor with other names), a loop of its own, one more hint, and the same ledger, rules and verification. A vendor without a domain is researched in the four news categories, and the model's 8 searches and 12 reads are split again (a category of the site 1 search, the news categories 2, 2, 1 and 1, and the reads 2 each; four loops of 2 searches and 3 reads for a vendor without a domain). No database holds the finances of a private company, so the category is the news alone. **The sanctions list** is a sixth source of records of the category `legal_regulatory`: the code looks the vendor up in the Specially Designated Nationals and Blocked Persons List of the Office of Foreign Assets Control of the United States Treasury, read from the two public files of the Sanctions List Service (`SDN.CSV` and `ALT.CSV`, no key; the process loads them once and keeps them for 6 hours, so a run never waits for a download longer than the 8,000 ms of the records). Only entities are matched, not people, vessels or aircraft, by name alone and letter for letter (the names and other names of the vendor against the names and aliases of the entry, with the legal form left out on both sides, at least 4 letters and digits), at most 2 records. A record is a source that was read, at the entry in the Sanctions List Search, and its text holds the entry, its programs, its other names, its remarks and the note that the vendor was matched by name only. One record is one publisher, so a finding that cites it is capped at `low`, and the prompt says that a match by name alone is a reason to check who the vendor is and never a finding that the vendor is sanctioned: the likelihood is no more than possible and the action is to compare the registration, the country and the owners with the entry. A run that cannot wait for the first download has the lookup failed as unreachable with no rest, and the next run has the list. No new migration (the one of `availability` had already widened the CHECK), no endpoint, no environment variable; the client has the category, its label and the translations in German, French and Spanish. See [web-research](../../technical/infrastructure/web-research.md#records-of-public-databases) and [vendors](../../technical/domains/vendors.md).
